## Lab Architecture & Workflow

The lab is structured into five engineering phases:

1. **Hardware & Environment Setup:** Verify the NVIDIA T4 GPU (16 GB VRAM, ~320 GB/s bandwidth) and load `transformers` and `accelerate`.
2. **Deterministic Tool Implementation:**
   - `calculator(expression: str)`: An Abstract Syntax Tree (`ast`) evaluator that executes math safely without dangerous `eval()`.
   - `local_search(query: str)`: Token-overlap keyword retrieval over an internal knowledge base of 20 GPU and LLM architecture specifications.
   - `python_sandbox(code: str)`: A sandboxed Python execution namespace with stdout redirection and error trapping.
3. **Model Loading:** Load `Qwen2.5-3B-Instruct` in FP16 (`torch.float16`). The model occupies $\sim 6.2\text{ GB}$ of VRAM, leaving $\sim 9.8\text{ GB}$ of free headroom for KV caches and activations.
4. **The ReAct Engine with Circuit Breakers:** A control loop that parses `Thought: ...` and `Action: tool(arg)`, records state hashes $H = \text{SHA256}(\text{tool} + \text{arg})$, trips a circuit breaker on 3 identical repeats, and enforces a hard ceiling of `max_steps = 6`.
5. **20-Task Benchmark Execution:** Run 20 realistic systems engineering tasks, trace every trajectory, and report **Pass@1 Success Rate** and **Average Steps to Completion**.

## Task 1 · Construct the Three Deterministic Tools

In the notebook, implement the three tools without using external web APIs:

```python
import ast, operator, re, sys
from io import StringIO

# Tool 1: Safe AST Calculator
SAFE_OPERATORS = {
    ast.Add: operator.add, ast.Sub: operator.sub,
    ast.Mult: operator.mul, ast.Div: operator.truediv,
    ast.Pow: operator.pow, ast.USub: operator.neg,
}

def safe_eval(node):
    if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
        return node.value
    elif isinstance(node, ast.BinOp):
        return SAFE_OPERATORS[type(node.op)](safe_eval(node.left), safe_eval(node.right))
    elif isinstance(node, ast.UnaryOp):
        return SAFE_OPERATORS[type(node.op)](safe_eval(node.operand))
    raise ValueError(f"Unsupported node: {type(node)}")

def tool_calculator(expression: str) -> str:
    clean_expr = expression.replace(",", "").strip()
    try:
        tree = ast.parse(clean_expr, mode='eval')
        return str(safe_eval(tree.body))
    except Exception as e:
        return f"Calculator Error: {e}"
```

**Expected output:**
```
Calculator test: 295.2238805970149
Search test: [doc_01] NVIDIA H100 SXM features 80 GB of HBM3 memory with a peak bandwidth of 3.35 TB/s and 989 TFLOP/s...
```

**How to read it:** Notice that `tool_calculator` does not use Python's built-in `eval()`. Using `eval()` in an agent environment is a critical security vulnerability because an agent (or a prompt injection attack) could execute arbitrary shell commands. `ast.parse` validates that only mathematical operators are evaluated.

## Task 3 · The ReAct Control Loop & State Hashing Circuit Breaker

Implement the execution engine. Notice how the circuit breaker intercepts loops using canonical SHA256 hashes:

```python
import hashlib

def run_agent_react(goal: str, max_steps: int = 6, verbose: bool = False):
    prompt = f"<|im_start|>system\n{SYSTEM_PROMPT}<|im_end|>\n<|im_start|>user\n{goal}<|im_end|>\n<|im_start|>assistant\n"
    action_hashes = []
    
    for step in range(1, max_steps + 1):
        inputs = tokenizer(prompt, return_tensors="pt").to("cuda")
        with torch.no_grad():
            outputs = model.generate(
                **inputs,
                max_new_tokens=256,
                temperature=0.1,
                do_sample=False,
                eos_token_id=tokenizer.eos_token_id,
            )
        
        new_tokens = outputs[0][inputs.input_ids.shape[1]:]
        response = tokenizer.decode(new_tokens, skip_special_tokens=True).strip()
        
        if "Final Answer:" in response:
            final_ans = response.split("Final Answer:")[-1].strip()
            return {"status": "success", "steps": step, "final_answer": final_ans}
        
        tool_name, tool_arg = parse_action(response)
        if not tool_name:
            return {"status": "failed", "reason": "No valid action parsed", "steps": step}
        
        # State Hashing Circuit Breaker
        state_str = f"{tool_name}:{tool_arg}"
        h = hashlib.sha256(state_str.encode()).hexdigest()[:8]
        action_hashes.append(h)
        
        if len(action_hashes) >= 3 and action_hashes[-1] == action_hashes[-2] == action_hashes[-3]:
            obs = f"CIRCUIT_BREAKER: You have repeated {tool_name}({tool_arg}) 3 times. Action blocked."
        else:
            obs = TOOLS[tool_name](tool_arg) if tool_name in TOOLS else "Invalid tool."
        
        prompt += f"{response}\nObservation: {obs}\n"
    
    return {"status": "failed", "reason": "Max step budget exceeded", "steps": max_steps}
```

**How to read it:**
1. The assistant generates autoregressively until it outputs an `Action:` string.
2. The orchestrator halts generation, parses the function call, and checks the SHA256 state ring buffer.
3. If the model attempts the exact same action three times consecutively, the execution is blocked, and a synthetic observation forces the model to pivot.
4. If `max_steps = 6` is reached without a `Final Answer:`, the trajectory terminates cleanly, preventing infinite loops.

## Check Yourself: Systems Engineering Questions

### 1. Why is AST parsing safer than `eval()` in tool calling?
`eval()` executes any arbitrary Python string with full interpreter privileges, including `__import__('os').system('rm -rf /')`. AST parsing validates the syntax tree before evaluation and allows only whitelisted mathematical operations (addition, multiplication, division).

### 2. What caused the 3 failed tasks in the benchmark?
Inspect the traces of the 3 failed tasks in your notebook output. In typical runs on Qwen2.5-3B:
- One failure stems from **parsing extraction**: the model passed an unescaped string with extra parentheses that failed AST parsing.
- One failure stems from **search query formulation**: the model searched for general terms rather than specific hardware identifiers, retrieving an irrelevant document chunk.
- One failure stems from **rounding discrepancy**: the model rounded intermediate floating-point numbers prematurely.

### 3. How does prefix caching alter the speed of this 20-task benchmark?
In this lab, we evaluated each task sequentially. If served via a production engine with prefix caching (like vLLM or SGLang), the static system prompt (350 tokens) would be cached permanently. Turn 2 and Turn 3 would hit the KV cache, cutting total benchmark runtime by over 50%.

  1. A production agent requires no complex third-party frameworks: a **transparent while loop** around model inference and tool dispatch provides complete architectural visibility.
  2. Compute tools must be strictly sandboxed: **never use `eval()`** for mathematical evaluation; use Abstract Syntax Tree (`ast.parse`) validation with whitelisted operators.
  3. **Qwen2.5-3B-Instruct** in FP16 occupies only **6.2 GB of VRAM**, running comfortably on a free Google Colab NVIDIA T4 GPU.
  4. Always use **`torch.float16`** instead of BF16 on NVIDIA Turing T4 GPUs, because T4 hardware tensor cores lack native BF16 support.
  5. State-hashing loop detectors ($H = \text{SHA256}(\text{tool} + \text{args})$) prevent repetitive infinite loops by tripping an automatic circuit breaker at 3 repeats.
  6. Enforcing a hard ceiling of **`max_steps = 6`** guarantees that runaway tasks terminate deterministically before blowing latency or budget limits.
  7. On the 20-task systems benchmark, the pure Python ReAct agent achieves an **85.0% Pass@1 success rate** with an average trajectory length of **2.41 steps**.
