You deploy a RAG-powered internal documentation assistant to 500 engineers. Within an hour, an incident lead flags an erroneous response:
- User prompt: *"What is the fallback retry policy for the message broker when a partition leader rebalances?"*
- Assistant reply: *"The message broker disconnects all consumer groups permanently and requires a manual service restart."*

This answer is dangerously incorrect. The lead engineer files a high-priority bug report: *"The AI assistant is hallucinating."*

As an inference systems engineer, you must answer an immediate diagnostic question: **Which subsystem failed?**

1. **Did the retriever fail?** Did the search index fail to locate the partition rebalancing runbook, returning 5 irrelevant documents about consumer group offset commits? (In which case the generator was starved of facts).
2. **Did the generator fail?** Did the retriever correctly place the rebalancing runbook at Rank 1 in the context, but the LLM ignored the text and fabricated a response anyway?

If you treat the system as a monolithic black box and evaluate only the final text output, you will waste weeks tuning LLM system prompts when the true defect was a missing keyword in the BM25 inverted index.

To engineer reliable RAG systems, we decouple evaluation into two independent disciplines: **Retriever Evaluation** and **Generator Evaluation**.

## The RAG Triad: Three orthogonal dimensions

The most widely adopted production evaluation framework is the **RAG Triad** (formalized by TruLens and adopted across enterprise LLM stacks). It breaks RAG quality into three checkable questions:

```
                  ┌──────────────────────┐
                  │      User Query      │
                  └──────────┬───────────┘
                             │
            Query-Context    │      Query-Answer
            Relevance        │      Relevance
                             ▼
┌──────────────────┐  Context-Answer   ┌──────────────────┐
│ Retrieved Context│ ────────────────> │ Generated Answer │
└──────────────────┘   Faithfulness    └──────────────────┘
```

### 1. Context Relevance (Retriever)
- **Question:** *Are the retrieved chunks relevant to the user query?*
- **Target:** High signal-to-noise ratio. Chunks should directly address the question without injecting thousands of tokens of irrelevant boilerplate.
- **Why it matters:** Extra noise triggers the *lost in the middle* phenomenon, increases prefill latency, and wastes GPU KV cache memory.

### 2. Groundedness / Faithfulness (Generator)
- **Question:** *Is every claim in the generated answer strictly supported by the retrieved context?*
- **Target:** 100% adherence to provided facts. Zero unverified extrapolation or hallucination.
- **Why it matters:** If the context says *"Timeout is 1,200 ms"* and the model outputs *"Timeout is 1,200 ms with 3 retries"*, the retry claim is unfaithful.

### 3. Answer Relevance (Generator)
- **Question:** *Does the generated response directly answer what the user asked?*
- **Target:** Responsiveness to user intent.
- **Why it matters:** A response can be 100% faithful to the context while completely ignoring the user's question (e.g., repeating context without answering the specific query).

## Retriever metrics: Precision@k and Recall@k

When evaluating a retriever on an offline benchmark, we have a test dataset of $Q$ queries, where each query has a ground-truth set of labeled relevant documents $\text{Rel}_q \subset C$.

When the retriever returns a ranked list of the top $k$ candidates $\text{Ret}_k(q)$:

### 1. Precision@k
The proportion of retrieved documents that are actually relevant:

$$
\text{Precision}@k = \frac{|\text{Ret}_k(q) \cap \text{Rel}_q|}{k}
$$

### 2. Recall@k
The proportion of total relevant documents that were successfully retrieved in the top $k$:

$$
\text{Recall}@k = \frac{|\text{Ret}_k(q) \cap \text{Rel}_q|}{|\text{Rel}_q|}
$$

<Callout type="math" title="Worked Example: Precision@5 and Recall@5">
  Suppose for a given technical query, your database contains **$|\text{Rel}_q| = 4$ ground-truth documents** that hold the answer.
  
  Your retriever returns $k = 5$ documents. Upon inspection against ground truth:
  - Rank 1: **Relevant**
  - Rank 2: Irrelevant
  - Rank 3: **Relevant**
  - Rank 4: Irrelevant
  - Rank 5: Irrelevant
  
  Number of retrieved relevant documents: $|\text{Ret}_5 \cap \text{Rel}| = 2$.
  
  $$
  \text{Precision}@5 = \frac{2}{5} = \mathbf{0.40}\ (40\%)
  $$
  
  $$
  \text{Recall}@5 = \frac{2}{4} = \mathbf{0.50}\ (50\%)
  $$
</Callout>

### The Trade-off Between k and Metrics
As $k$ increases (e.g. from $k = 3$ to $k = 50$):
- **Recall@k monotonically increases** (or stays constant). The wider the net you cast, the higher the probability you capture the relevant documents.
- **Precision@k typically decreases**. Most queries have only 1 to 3 truly relevant documents. Forcing $k = 20$ means at least 17 documents are guaranteed to be irrelevant, dragging precision down.

In RAG pipelines, **Recall@k is the primary survival metric for Stage 1 retrieval**. If the ground truth document is not in the top 100 candidates returned by Stage 1, no downstream reranker or generator can ever see it.

## Ranking metrics: MRR and NDCG

Binary Precision and Recall treat the retrieved set as an unordered bucket: a relevant document at Rank 1 is treated identically to a relevant document at Rank 10.

In transformer inference, position matters tremendously:
- Attention heads exhibit a U-shaped attention curve (**lost in the middle**, Module B1): facts at the very top or bottom of the prompt receive far higher attention weights than facts buried in the middle.
- If a relevant document is at Rank 1, the LLM finds it immediately and generates a grounded response. If the same document is at Rank 8, the generator may overlook it or run out of context.

We need metrics that explicitly penalize poor ordering.

### Mean Reciprocal Rank (MRR)
MRR focuses on a single critical event: **Where does the FIRST relevant document appear?**

For a query $i$, let $\text{rank}_{1, i}$ be the 1-based position of the first relevant result:

$$
\text{RR}_i = \frac{1}{\text{rank}_{1, i}}
$$

Across a benchmark suite of $|Q|$ queries:

$$
\text{MRR} = \frac{1}{|Q|} \sum_{i=1}^{|Q|} \frac{1}{\text{rank}_{1, i}}
$$

- If the first relevant document is at Rank 1: $\text{RR} = 1/1 = 1.0$.
- If the first relevant document is at Rank 2: $\text{RR} = 1/2 = 0.5$.
- If the first relevant document is at Rank 4: $\text{RR} = 1/4 = 0.25$.
- If no relevant document is found in the top $k$: $\text{RR} = 0.0$.

<Callout type="math" title="Worked Example: MRR Across 3 Queries">
  Evaluate a retriever across 3 evaluation benchmark queries:
  
  - **Query 1:** First relevant document found at **Rank 1** $\implies \text{RR}_1 = \frac{1}{1} = 1.000$
  - **Query 2:** First relevant document found at **Rank 4** $\implies \text{RR}_2 = \frac{1}{4} = 0.250$
  - **Query 3:** First relevant document found at **Rank 2** $\implies \text{RR}_3 = \frac{1}{2} = 0.500$
  
  The Mean Reciprocal Rank is:
  
  $$
  \text{MRR} = \frac{1.000 + 0.250 + 0.500}{3} = \frac{1.750}{3} \approx \mathbf{0.583}
  $$
</Callout>

MRR is ideal for question-answering systems where a single concise passage is sufficient to answer the prompt.

### Normalized Discounted Cumulative Gain (NDCG)
When queries require synthesizing information across multiple documents, or when documents have **graded relevance**, the gold standard is **NDCG@k**.

Relevance is graded on an integer scale, typically:
- **3:** Perfect match (exact answer to user's question).
- **2:** Highly relevant (contains key supporting details).
- **1:** Marginally relevant (on topic, but lacks specific answer).
- **0:** Irrelevant (junk / noise).

#### Step 1: Discounted Cumulative Gain (DCG@k)
DCG sums the graded relevance of retrieved documents, penalizing documents that appear at lower rank positions using a logarithmic discount:

$$
\text{DCG}@k = \sum_{i=1}^k \frac{2^{\text{rel}_i} - 1}{\log_2(i + 1)}
$$

- The numerator $2^{\text{rel}_i} - 1$ exponentially rewards high-grade documents ($2^3 - 1 = 7$, $2^2 - 1 = 3$, $2^1 - 1 = 1$, $2^0 - 1 = 0$).
- The denominator $\log_2(i + 1)$ logarithmic discounts position:
  - $i = 1 \implies \log_2(2) = 1.000$
  - $i = 2 \implies \log_2(3) \approx 1.585$
  - $i = 3 \implies \log_2(4) = 2.000$
  - $i = 4 \implies \log_2(5) \approx 2.322$
  - $i = 5 \implies \log_2(6) \approx 2.585$

#### Step 2: Ideal Discounted Cumulative Gain (IDCG@k)
What is the best possible score this retriever could have achieved?

Sort the ground-truth relevance grades in descending order (the ideal ranking) and compute DCG on that sorted list:

$$
\text{IDCG}@k = \sum_{i=1}^k \frac{2^{\text{rel}^*_i} - 1}{\log_2(i + 1)}
$$

#### Step 3: Normalized DCG (NDCG@k)

$$
\text{NDCG}@k = \frac{\text{DCG}@k}{\text{IDCG}@k}
$$

Because DCG is divided by the ideal sort, NDCG is strictly bounded between **$0.0$ and $1.0$**. A score of $1.0$ indicates a mathematically perfect ranking.

<Callout type="math" title="Worked Example: Step-by-Step NDCG@4 Calculation">
  Suppose for a query, the retriever returns 4 documents with actual relevance grades:
  $$
  \text{Grades} = [3, 0, 2, 1]
  $$

  **1. Compute DCG@4:**
  - Position 1 ($\text{rel}_1 = 3$): $\frac{2^3 - 1}{\log_2(1 + 1)} = \frac{7}{1.000} = 7.000$
  - Position 2 ($\text{rel}_2 = 0$): $\frac{2^0 - 1}{\log_2(2 + 1)} = \frac{0}{1.585} = 0.000$
  - Position 3 ($\text{rel}_3 = 2$): $\frac{2^2 - 1}{\log_2(3 + 1)} = \frac{3}{2.000} = 1.500$
  - Position 4 ($\text{rel}_4 = 1$): $\frac{2^1 - 1}{\log_2(4 + 1)} = \frac{1}{2.322} \approx 0.431$

  $$
  \text{DCG}@4 = 7.000 + 0.000 + 1.500 + 0.431 = \mathbf{8.931}
  $$

  **2. Compute Ideal Sort & IDCG@4:**
  Sort grades descending: $[3, 2, 1, 0]$
  - Position 1 ($\text{rel}^*_1 = 3$): $\frac{7}{1.000} = 7.000$
  - Position 2 ($\text{rel}^*_2 = 2$): $\frac{3}{1.585} \approx 1.893$
  - Position 3 ($\text{rel}^*_3 = 1$): $\frac{1}{2.000} = 0.500$
  - Position 4 ($\text{rel}^*_4 = 0$): $\frac{0}{2.322} = 0.000$

  $$
  \text{IDCG}@4 = 7.000 + 1.893 + 0.500 + 0.000 = \mathbf{9.393}
  $$

  **3. Compute NDCG@4:**
  $$
  \text{NDCG}@4 = \frac{\text{DCG}@4}{\text{IDCG}@4} = \frac{8.931}{9.393} \approx \mathbf{0.951}
  $$

  The retriever scored an excellent **$0.951$** because its highest-value document ($\text{rel}=3$) was placed squarely at Rank 1.
</Callout>

## Evaluating the generator: Faithfulness & LLM-as-a-Judge

Once you have verified that your retriever achieves high Recall@k and NDCG, how do you measure generator faithfulness at production scale?

Human evaluation is slow, expensive, and unscalable. The standard production solution is **LLM-as-a-Judge** (evaluated in depth in Module B2).

To measure **Faithfulness**:
1. Deconstruct the generated answer into individual atomic factual statements.
2. For each atomic statement, ask a judge model to verify whether the statement is directly entailed by the retrieved context.

Here is a production prompt template for assessing faithfulness:

```python
FAITHFULNESS_PROMPT = """You are an impartial evaluator assessing the groundedness of an AI response.
Your task is to determine whether every factual assertion in the generated answer is directly supported by the provided context.

Context:
{context}

Generated Answer:
{answer}

Follow this procedure:
1. Break down the Generated Answer into a bulleted list of discrete, atomic factual statements.
2. For each statement, determine whether it is ENTAILED by the Context, CONTRADICTED by the Context, or NOT MENTIONED in the Context.
3. Calculate the Faithfulness Score as: (Number of Entailed Statements) / (Total Number of Statements).

Output JSON with format:
{{
  "statements": [
    {{"claim": "statement text", "verdict": "ENTAILED | CONTRADICTED | NOT_MENTIONED"}}
  ],
  "score": float
}}
"""
```

If an answer contains 4 claims and 3 are supported while 1 is unmentioned, its Faithfulness Score is:

$$
\text{Faithfulness} = \frac{3}{4} = 0.75
$$

Any query dropping below $1.0$ is flagged in production telemetry as a potential hallucination.

<KeyNotes>
  1. Never evaluate RAG as a monolithic black box. **Separate retriever evaluation from generator evaluation** to identify true root causes of failure.
  2. The **RAG Triad** measures three dimensions: **Context Relevance** (retriever quality), **Faithfulness** (generator adherence to context), and **Answer Relevance** (addressing user prompt).
  3. **Precision@k** is the fraction of the top $k$ retrieved chunks that are relevant; **Recall@k** is the fraction of total corpus relevant chunks captured in the top $k$.
  4. In Stage 1 candidate generation, **Recall@k is the vital survival metric**: if a document is missed at Stage 1, downstream components can never recover it.
  5. **Mean Reciprocal Rank (MRR)** measures the position of the *first* relevant result: $\text{RR} = 1 / \text{rank}_1$.
  6. **Discounted Cumulative Gain (DCG)** accounts for graded relevance (0 to 3) with a logarithmic discount: $\sum \frac{2^{\text{rel}_i} - 1}{\log_2(i + 1)}$.
  7. **NDCG@k** normalizes DCG by the ideal ranking (IDCG), producing a metric in $[0, 1]$ where $1.0$ represents a perfect rank ordering.
</KeyNotes>
