Everything in the last three lessons assumed a fleet that somebody had built: replicas that start, a router that knows about them, an autoscaler that adds more. This lesson is about the part that actually builds it — the stack of software between your HTTP handler and the GPU.

The trap is that this stack was designed for web servers, and an inference replica is not one.

## The five layers

Whatever the technology, every LLM deployment is the same five layers:

1. **Your application** — clients, streaming, authentication, your business logic.
2. **Routing** — which replica gets this request (Lesson 23.1).
3. **Scaling** — how many replicas exist (Lesson 23.3).
4. **Replicas** — the engine process holding the weights and the KV cache.
5. **The GPU** — where the work happens.

Layers 2 and 3 are what you learned today. Layers 4 and 5 are Modules 05 through 22. Layer 1 is your product. The interesting question is: **which technology sits where, and who has to maintain it?**

  <Step title="1. The five layers">
    Every deployment, from a laptop to a thousand-GPU cluster, is this stack. The bottom three layers are shared infrastructure that works the same for any container. The top two are where LLM inference genuinely differs from serving an ordinary API.
  </Step>

  <Step title="2. Kubernetes is the substrate">
    Nodes, pods, Deployments, Services, Ingress. Kubernetes schedules pods, restarts the ones that die, discovers them through a Service, and gives them DNS names. It is a genuinely excellent substrate — and it has never heard of a token, a KV cache or a GPU.
  </Step>

  <Step title="3. A pod is not a replica">
    A web pod is cheap, interchangeable and disposable. An inference replica holds 16 GB of loaded weights, a populated KV cache, and the in-flight state of real users' conversations. It wants a whole node, pinned devices, large shared memory, and minutes to drain on shutdown.
  </Step>

  <Step title="4. KServe: inference as a resource">
    KServe's premise: a model should be a Kubernetes resource, not a program you write. You declare an `InferenceService` — model, runtime, autoscaler — and a controller reconciles it into a deployment, a Service, an HPA and an ingress. Minimum code, minimum control.
  </Step>

  <Step title="5. Ray Serve: requests as objects">
    Ray's premise: the *request* is the primitive. You write a `@app.deployment` class and Ray handles placement, continuous batching across replicas, request routing and scale-to-zero. More power, and all of it is code you now maintain.
  </Step>

  <Step title="6. llm-d: scheduling as its own layer">
    llm-d's premise: inference has a scheduling problem that generic Kubernetes scheduling cannot express — cache locality, prefix affinity, prefill/decode balance. So it adds a scheduler-aware control plane that treats placement as a first-class decision.
  </Step>

  <Step title="7. Choosing a layer">
    Choose by how much you want to own. KServe if you want Kubernetes to own it, Ray Serve if you want to program the serving logic yourself, llm-d if the scheduling itself is where you think the advantage is. Everything above the line is code someone has to page at 3am.
  </Step>
</Scrolly>

## Why GPU replicas break the web-server pod model

A pod is defined by four assumptions that hold for a web server and fail for an <Term t="inference-replica">inference replica</Term>:

**Small state.** A web pod holds a few megabytes. An inference replica holds the model's weights — 16 GB for Llama-8B in BF16 — plus a KV cache that grows to tens of gigabytes. You cannot casually run ten of these on one node and expect them to behave.

**Fast start.** A web pod is serving requests within a second. An inference replica must load weights from disk or network, allocate its KV pool, and warm up (Module 22) — tens of seconds to several minutes. This is why scaling has to be anticipatory.

**Cheap to replace.** Kubernetes kills and recreates pods freely. Killing a pod that holds live KV cache kills real users' in-flight conversations, so you need <Term t="draining">draining</Term>, preStop hooks and a generous `terminationGracePeriodSeconds`.

**One GPU, one process.** Multi-GPU inference needs collective communication (Module 18), which means the GPUs must be on the same node with a topology-aware placement, shared memory configured, and often `hostIPC` and huge pages enabled.

In practice the manifest grows accordingly. Note the <Term t="termination-grace">termination grace period</Term>, which is minutes rather than seconds:

```yaml
# A rough shape of what an inference pod actually needs. Illustrative.
spec:
  terminationGracePeriodSeconds: 600   # drain, do not kill
  containers:
    - name: engine
      command: ["vllm", "serve", "meta-llama/Llama-3.1-8B"]
      env:
        - name: VLLM_WORKER_MULTIPROC_METHOD
          value: spawn
      resources:
        limits:
          nvidia.com/gpu: 1
          sharedmemory: 16Gi      # paged KV + NCCL need it
      startupProbe:                # "ready" only after weights load
        httpGet: { path: /health, port: 8000 }
        failureThreshold: 60
        periodSeconds: 5
      lifecycle:
        preStop: { exec: { command: ["sh","-c","sleep 15"] } }
```

Notice the `startupProbe` rather than a readiness probe: the pod is *alive* long before it is *able to serve*, and a liveness probe that fires during weight loading will restart the pod in a loop forever. That distinction is the single most common failure when putting vLLM behind Kubernetes, and it is why the <Term t="startup-probe">startup probe</Term> exists as a separate primitive.

<Callout type="pitfall" title="The liveness-probe restart loop, and why it costs you your KV cache">
  Point a liveness probe at an endpoint that does not answer until the model is loaded, and Kubernetes concludes the container is hung. It kills it and starts a new one, which loads the weights again, which does not answer the probe. The result is a pod that restarts every thirty seconds, burns the image pull quota, and never serves a request. Use a <Term t="startup-probe">`startupProbe`</Term> with a generous threshold, then a liveness probe that only checks the process is alive.
</Callout>

## The three tools, honestly compared

| | KServe | Ray Serve | llm-d |
|---|---|---|---|
| **Abstraction** | `InferenceService` CRD | `@app.deployment` class | Gateway + placement layer on k8s |
| **You write** | YAML | Python | YAML + optional components |
| **Owns** | reconciliation, ingress, HPA wiring | placement, batching, routing, scale-to-zero | routing, topology-aware placement |
| **Scheduling awareness** | basic (HPA on queue/GPU) | good (programmable) | the point of the project |
| **Scale to zero** | yes | yes, built-in | depends on setup |
| **Learning curve** | Kubernetes | Ray | both |
| **Best when** | you already run k8s and want it to just work | serving logic is genuinely custom | placement/locality is your differentiator |

**KServe** (<Term t="kserve">KServe</Term>) is the pragmatic default. It wins because everything you already know about Kubernetes — RBAC, network policies, secrets, canaries from Module 22, Prometheus metrics — keeps working, and because a controller doing reconciliation is far less code for you to maintain at 3am.

**Ray Serve** (<Term t="ray-serve">Ray Serve</Term>) wins when your serving logic is genuinely custom: you need per-request Python, complex batching policies, model multiplexing with a shared queue, or you want the same framework for training and serving. Its real advantage is that continuous batching across replicas is a first-class concept rather than something you bolted onto HTTP.

**llm-d** (<Term t="llm-d">llm-d</Term>) is the interesting bet, and at the time of writing it is young. Its thesis is the correct one — the placement problem is genuinely different for inference, and prefill/decode balance and cache locality belong in the scheduler. If it delivers, it is a real advantage; if you adopt it early, you are adopting a moving target.

<Callout type="real" title="A fourth option worth knowing">
  vLLM ships with a production stack of its own: an API server, a router that can be cache-aware, and workers managed directly, without Kubernetes at all. For a fleet of ten to fifty replicas on a fixed set of machines, this is often the *lowest* operational burden, because there is no cluster to operate. Reach for a cluster when you need to scale across machines you do not own or when the org already runs one.
</Callout>

## Choosing, concretely

Decide by asking three questions in order:

1. **Do you already run Kubernetes?** If yes, KServe costs you the least. If no, and your fleet is under ~50 replicas on machines you control, vLLM's own stack or a plain process manager may be less work than adopting a cluster.
2. **Is the serving logic unusual?** Multi-model routing with model-specific batching, custom tokenization, or application-level logic in the request path all argue for Ray Serve.
3. **Is placement your differentiator?** If you are betting that cache-aware routing and prefill/decode balance are where the performance comes from, that argues for a layer that treats them as first-class — which is llm-d's reason to exist.

<Callout type="mentor" title="What to say in a design review">
  "We run on Kubernetes because the org already operates it, so the marginal cost of KServe is a CRD rather than a cluster. We keep the router in front of the engines rather than relying on a Service, because routing on KV load is worth more than the operational simplicity we would buy. We revisit llm-d when placement becomes our bottleneck, not before."
</Callout>

## Many models behind one front door

So far every replica served one model. Real fleets rarely look like that. A platform team might host forty fine-tuned 8B models, one per customer or task, plus two base models and a canary of the next version. Give each its own GPU and most of those GPUs sit idle, because traffic across models is lopsided: a few models take most of the requests and the long tail takes a trickle. The answer has three parts, and they live at layer 3 of the enterprise map below: a **router** that decides which model a request should get, **multiplexing** that decides which replica should serve it, and a **cache** on each replica that decides which models stay loaded.

### Part 1: the model-selection router

A request names a model, but not always the real one. A <Term t="model-selection-router">model-selection router</Term> is a small, pure function that turns *what the client asked for* into *what will actually run*, and it does three jobs:

```python
import hashlib

ALIASES = {"chat": "llama-3.1-8b-instruct-v7", "chat-large": "llama-3.1-70b-instruct-v3"}
ALLOWED = {                                    # per-tenant allow-lists
    "acme":   {"llama-3.1-8b-instruct-v7", "acme-support-v2"},
    "globex": {"llama-3.1-8b-instruct-v7", "llama-3.1-70b-instruct-v3"},
}
CANARY = {                                     # weighted splits for a stable name
    "llama-3.1-8b-instruct-v7": [("llama-3.1-8b-instruct-v7", 0.95),
                                 ("llama-3.1-8b-instruct-v8", 0.05)],
}

def select_model(tenant: str, user: str, requested: str) -> str:
    name = ALIASES.get(requested, requested)           # 1. resolve the alias
    if name not in ALLOWED.get(tenant, set()):          # 2. enforce the tenant's allow-list
        raise PermissionError(f"{tenant} may not use {name}")
    splits = CANARY.get(name)                           # 3. weighted canary split
    if not splits:
        return name
    h = int(hashlib.sha256(f"{name}:{user}".encode()).hexdigest(), 16)
    u, acc = (h % 10_000) / 10_000, 0.0                 # stable per user, uniform overall
    for target, weight in splits:
        acc += weight
        if u < acc:
            return target
    return splits[-1][0]
```

Three details are deliberate. **Aliases** let clients ask for "chat" while you swap the model underneath. The **allow-list** is checked against the stable name before the canary, so a tenant permitted to use v7 is automatically permitted to receive its canary and nobody else's. And the split hashes the **user**, not a random number, so one user sees one version for a whole conversation instead of flipping between v7 and v8 every turn (Python's built-in `hash()` changes between processes, which is why this uses `hashlib`). At 2,000 requests a minute, a 5% split sends about **100 requests a minute** to v8: 1,000 within ten minutes, enough to compare its p95 TTFT and error rate with v7's before you ramp (Module 22).

### Part 2: multiplexing many models onto few replicas

Now the router has said "acme-support-v2". Which replica should run it? Ideally one that already has it loaded. **Ray Serve** has this built in as <Term t="model-multiplexing">**model multiplexing**</Term>: each replica keeps up to a fixed number of models in memory, and the router prefers replicas that already hold the requested one.

```python
from ray import serve

@serve.deployment(ray_actor_options={"num_gpus": 1})
class ManyModels:
    @serve.multiplexed(max_num_models_per_replica=3)
    async def get_model(self, model_id: str):
        return await load_model(model_id)               # runs only on a miss on this replica

    async def __call__(self, request):
        model_id = serve.get_multiplexed_model_id()     # which model this request wants
        model = await self.get_model(model_id)          # hit: already loaded; miss: load, evict LRU
        return await model.generate(await request.json())

app = ManyModels.bind()
```

The client (or the router in front) puts the model id in a request header, `serve_multiplexed_model_id` at the time of writing, and `serve.get_multiplexed_model_id()` reads it back inside the replica. When a replica already holds three models and a fourth is requested, it evicts its <Term t="lru-eviction">**least recently used**</Term> one. **The arithmetic decides whether this works.** Eight replicas × 3 slots = 24 resident models. If the 16 least popular of 40 models together draw 5% of requests and none of them is resident anywhere, then 1 request in 20 pays a cold load: 16 GB of weights at about 2 GB/s from local NVMe is about 8 s of TTFT. Your p50 is untouched and your p99 is a model load. Either add slots (smaller models, more memory, LoRA adapters instead of full models; see Multi-LoRA serving) or pin the tail to a dedicated replica where its cold starts are expected.

### Part 3: build the per-replica LRU cache yourself

The eviction rule inside each replica is worth writing once, because every multi-model server has one. An `OrderedDict` remembers insertion order, and two of its methods make LRU a few lines: `move_to_end(key)` marks a model as just used, and `popitem(last=False)` removes the one used longest ago.

```python
from collections import OrderedDict

class ModelCache:
    """Keep as many models resident as fit in capacity_gb; evict least recently used."""
    def __init__(self, capacity_gb: float, sizes_gb: dict, load, unload):
        self.capacity, self.sizes, self.load, self.unload = capacity_gb, sizes_gb, load, unload
        self.models = OrderedDict()                      # model_id -> model, oldest first
        self.used = 0.0

    def get(self, model_id: str):
        if model_id in self.models:                      # hit
            self.models.move_to_end(model_id)            # now the most recently used
            return self.models[model_id]
        need = self.sizes[model_id]                      # miss: make room BEFORE loading
        while self.models and self.used + need > self.capacity:
            old_id, old = self.models.popitem(last=False)   # least recently used
            self.unload(old)
            self.used -= self.sizes[old_id]
        self.models[model_id] = self.load(model_id)
        self.used += need
        return self.models[model_id]
```

Evict **before** you load: loading first would briefly need room for the newcomer and the model it is about to replace, which is exactly the out-of-memory you were trying to avoid. Trace it on an L40S with about 48 GB to spare and three 16 GB models' worth of room, for the request sequence A, B, C, A, D:

| request | hit or miss | evicted | resident afterwards, oldest first | used |
|---|---|---|---|---|
| A | miss | — | A | 16 GB |
| B | miss | — | A, B | 32 GB |
| C | miss | — | A, B, C | 48 GB |
| A | **hit** | — | B, C, **A** | 48 GB |
| D | miss | **B** | C, A, D | 48 GB |

The hit on A is what saved it: without `move_to_end`, A would have been the oldest and D would have evicted the model that was just in use.

## The rolling deploy, end to end

Module 22 taught canaries and rollbacks for one server. On a fleet the same release is a multi-step dance, and the ordering matters more than it did with one pod.

The safe sequence is: bring up the new replica, let it pass its health checks and take its first real request, then move a small share of traffic, then ramp. At each stage the question is whether the *new* replica's percentiles match the old fleet's. Because you route on KV load and a fresh replica has an empty cache, the newcomer looks like the least loaded thing in the fleet and will take a disproportionate share of traffic immediately — which is useful, because it exercises it, and risky, because a cold replica is slower for exactly the requests that need its prefix.

Two practices make this survivable. First, **warm the replica before it counts**: send it a synthetic prompt of representative length so its KV pool is allocated and its weights are resident, and only then add it to the router's candidate set. Second, **hold one replica of headroom** so the new version has somewhere to land traffic without the fleet shrinking. Both are the same lesson as scaling, applied to releases instead of demand.

<Callout type="pitfall" title="A cold replica will take more traffic than you intended">
  Every routing policy in this module prefers the least-loaded replica, and a replica that has just started is the least loaded thing that exists. So your canary does not receive 5% of traffic — it receives whatever the router thinks is fair, which on a cold cache is often far more. Warm it first, or cap its share explicitly, or your 5% canary is really a 60% canary that you believed was 5%.
</Callout>

## The enterprise map: seven layers, top to bottom

The five layers at the top of this lesson are what you deploy. A company that sells inference to many teams or customers needs a wider map, because three new jobs appear above the replicas — who may send what, how the GPUs are shared out, and which model answers — and the replica itself splits into three layers you tune in different ways.

Here is the whole system, from the request coming in at the top down to the weights at the bottom. For each layer: what it does, what you tune there, and where this course teaches it.

1. **Public API.** The front door clients see: it checks who is calling (authentication), which plan they are on (tiering), and whether they are under their quota and rate limit, and it rejects the rest before any GPU work happens. You tune the per-tier rate limits, the largest `max_tokens` and context a request may ask for, timeouts, and the error a rejected client gets back. Course: "Serving a model over HTTP", "Admission control, backpressure & load shedding" and "Securing an inference service".
2. **Resource management.** Decides how the GPUs are shared out: which pool of GPUs each tier or team runs on, each tenant's quota, and how much spare capacity each pool keeps. You tune pool sizes, per-tenant concurrency caps and KV shares, and the headroom each pool holds. Course: "Capacity planning & headroom", "Autoscaling on the right signals" and "Admission control, backpressure & load shedding".
3. **Model selection and orchestration.** Decides which model, version or adapter serves the request: a small model or a large one, the stable version or the canary, the base model or a tenant's LoRA. You tune routing thresholds, the escalation rate of a cascade, and canary share. Course: "Semantic caching & semantic routing", "Multi-model serving & Triton Inference Server", "Versioning, canaries, shadow traffic & rollbacks" and "Multi-LoRA serving".
4. **Distributed serving.** Decides which copy of the chosen model runs the request, and how one model is spread over many GPUs. You tune the routing policy, the parallelism layout, and the prefill-to-decode ratio. Course: "Load balancing & queue-aware routing", "Prefix- & cache-aware routing", "Tensor parallelism", "Why separate prefill and decode" and this lesson.
5. **Core inference engine.** The process on the GPU that batches requests step by step and manages the KV cache. You tune `max_num_seqs`, `max_num_batched_tokens`, `gpu_memory_utilization`, chunked prefill and prefix caching. Course: "Continuous batching", "The scheduler’s knobs: token budgets & limits", "Blocks, block tables & PagedAttention", "Prefix caching" and "Metrics & tuning one GPU".
6. **Model optimization.** Makes each forward pass cheaper without changing what the model is: fewer bits, faster kernels, fewer launches, several tokens per step. You tune the quantization scheme, the attention backend, CUDA graphs and the draft length. Course: "W4A16, W8A8, FP8: choosing a scheme", "Decode attention & attention backends", "CUDA graphs: capture & replay" and "Draft & verify: the core trick".
7. **The model itself.** The weights and the architecture, which fix the two numbers every layer above inherits: bytes of weights and bytes of KV per token. You choose the model size, the attention layout (GQA), dense or MoE, and the maximum context. Course: "Choosing an open model", "Multi-head attention, MQA & GQA", "How MoE works: routing tokens to experts" and "Memory math: weights, KV cache & concurrency".

Read the list from the bottom up and every layer is a budget handed to the one above it. The model fixes bytes per token; optimization shrinks them; the engine turns them into concurrency; distributed serving multiplies that across GPUs; model selection decides which of those fleets a request lands on; resource management splits the fleets between customers; and the public API decides who gets in. **A problem at one layer is often cheapest to fix one layer lower** — a tenant blowing through its quota is a layer-1 problem, but if every tenant does, the fix is a cheaper model at layer 6.

### Where the gateway ends and the router begins

Layers 1 and 2 are usually one service, the <Term t="api-gateway">API gateway</Term>. Layer 4 is the router from the first lesson of this module. They are easy to blur, and blurring them causes real bugs, so draw the line by what each one needs to know.

The **gateway** answers *may this request run, and at what priority?* It needs only the request and the tenant's own counters: the key, the tier, the tokens left in the quota, the request's size. It knows nothing about GPUs, so it scales like an ordinary web tier, and a rejection there costs nothing — a `429` sent before any prefill.

The **router** answers *where does this admitted request run?* It needs live state from every replica — KV tokens in use, queue depth, which prefixes are cached — and nothing about who the tenant is beyond a priority label.

Two failure modes follow. If the router enforces quotas, it must keep every tenant's counters in sync across router instances, and every rejection happens after the request has already been placed in a queue. If the gateway tries to balance load, it is back to counting connections, which is the problem Lesson 23.1 started with. Keep the gateway deciding *whether* and the router deciding *where*.

### Isolation, quotas and audit are serving requirements

On a shared fleet, three things a single-user server can ignore become part of serving:

- **Isolation.** One tenant must not be able to slow down or read another. That means a per-tenant concurrency cap and KV share (so one tenant's long prompts cannot fill the pool) and a tenant ID in every cache key, as in "Securing an inference service". The cost is a little less sharing in the prefix cache; the alternative is a data leak.
- **<Term t="token-quota">Quotas in tokens</Term>, not requests.** A request can be 40 tokens or 40,000, so a limit of "100 requests per minute" lets one tenant use a thousand times the GPU of another. Charge the quota in tokens — prompt plus output — because that is what the GPU actually spends.
- **Audit.** Every request leaves one <Term t="audit-record">audit record</Term>: tenant, model and version, prompt and output token counts, the admission decision and the latency. Billing, quota enforcement and incident review all read it, so the gateway should count tokens once and feed all three from that count. The record holds counts and IDs, not raw prompts, unless a tenant has agreed otherwise.

### A worked token bucket

The standard way to enforce a token quota is a <Term t="token-bucket">token bucket</Term>. The bucket holds up to $b$ tokens. It refills at a steady rate $r$ tokens per second. Each request takes its cost out of the bucket when it is admitted; if the bucket does not hold enough, the request is rejected (or waits).

Take a tenant on a plan of **60,000 tokens per minute** with a burst of **20,000**. Then:

$$
r = \frac{60{,}000}{60\ \text{s}} = 1{,}000\ \text{tokens/s}, \qquad b = 20{,}000\ \text{tokens}
$$

Each request has a 1,500-token prompt and asks for up to 500 output tokens. The gateway cannot know how many tokens the model will actually write, so it reserves the worst case at admission:

$$
c = 1{,}500 + 500 = 2{,}000\ \text{tokens per request}
$$

The tenant has been quiet, so the bucket is full. Then a batch job sends **30 requests at once**.

- **At t = 0:** the bucket holds 20,000, enough for $\lfloor 20{,}000 / 2{,}000 \rfloor = 10$ requests. Ten are admitted and the bucket is empty. The other 20 get a `429`.
- **After that:** the bucket refills 1,000 tokens a second, so a new request fits every 2,000 / 1,000 = 2 seconds. The 20 rejected requests need 20 × 2,000 = 40,000 tokens, which takes 40,000 / 1,000 = **40 seconds** to refill. If the client retries politely, the last request is admitted at t = 40 s.
- **Over the first minute:** the 30 requests reserved 30 × 2,000 = 60,000 tokens in 40 seconds, faster than the plan's rate of 1,000 a second would allow (40,000 in 40 s), because the burst came first. Had the job kept sending, the tenant could have spent the 20,000 burst plus 60 seconds of refill, 60,000 — **80,000 tokens** in one minute. In general the most a tenant can spend in any window of $T$ seconds is

$$
b + rT
$$

That last line is the one capacity planning needs. A "60,000 tokens a minute" plan really allows 80,000 in the worst minute, and the 10 requests at t = 0 land on the GPUs as a single spike. Those 10 requests reserve 20,000 tokens of KV. At Llama-3.1-8B's 131,072 bytes per token that is 2.6 GB, about 5% of the 402,000-token pool from the quiz below — harmless for one tenant. But if 50 tenants on this plan burst at the same moment, that is 50 × 20,000 = 1,000,000 tokens, about 2.5 replicas' entire KV pools. **Per-tenant buckets protect tenants from each other; only a global admission limit and headroom protect the fleet from all of them at once.**

```python
# A token bucket for one tenant: 60,000 tokens/min, burst of 20,000.
RATE = 60_000 / 60      # refill, tokens per second
BURST = 20_000          # bucket capacity
COST = 1_500 + 500      # prompt + max_tokens reserved per request

tokens, admitted = BURST, []
waiting = 30                       # 30 requests arrive at t = 0
for t in range(0, 61):             # one tick per second
    if t > 0:
        tokens = min(BURST, tokens + RATE)
    while waiting and tokens >= COST:
        tokens -= COST
        waiting -= 1
        admitted.append(t)

print(admitted.count(0), "admitted at t=0")             # 10
print("last of the 30 admitted at t =", admitted[-1])   # 40
```

<Callout type="pitfall" title="Reserving max_tokens punishes generous clients">
  Because the gateway reserves the prompt plus `max_tokens` up front, a client that sets `max_tokens` to 4,096 for answers that are really about 200 tokens reserves about 20 times the output it uses (4,096 / 200 ≈ 20), and hits its limit long before it has spent its quota. Good gateways refund the unused part when the request finishes. Good clients set `max_tokens` close to what they need. Both matter, and the refund is what makes the quota mean what the plan says.
</Callout>

  8. Route in front of the engines with something KV-aware; a plain Service cannot see the thing that matters.
  9. Many models share few GPUs in three steps: a model-selection router (aliases, per-tenant allow-lists, sticky weighted canary splits), multiplexing that sends a request to a replica already holding its model (Ray Serve: `@serve.multiplexed(max_num_models_per_replica=…)` and `serve.get_multiplexed_model_id()`), and a per-replica LRU cache (`OrderedDict` with `move_to_end` and `popitem(last=False)`, evicting before loading).
