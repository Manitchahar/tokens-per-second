In Module 03 you built a transformer in your head, and in Module 04 you ran one. Both ended with the same constraint: a model can only emit **one token per forward pass**, because every token it produces must be fed back in as the input for the next one. That is <Term t="autoregressive">autoregressive</Term> generation, and it is a design choice with a price tag.

Here is the price tag, and it is bigger than most people expect. The obvious way to write generation is to keep appending to a list of token IDs and call the model on the whole list every time. That loop is four lines long, it is easy to read, and it does about **a hundred times more arithmetic than it needs to** for a typical request. This lesson is about measuring that, understanding exactly *why* it happens, and being precise about how much it costs — because the honest answer is more interesting than the scary one.

## One token, one step

Start with the sequence. A prompt of 512 tokens goes in. The model runs a full forward pass and produces one number for every token in its 128,000-word vocabulary: which token should come next. You pick one, append it, and run the whole thing again.

The visual below shows what the model is asked to do on each of those steps. Scroll through it, then drag the sliders to see how the numbers move with prompt length and output length.

    The naive loop does not know that. It hands the entire sequence back to the model and lets it recompute every key, every value, every layer's output for every token. At step *t* that is 512 + *t* token-forwards, when one would do.

    Now the fix, which this module is entirely about. The old tokens' keys and values are **stored, not recomputed** — <Term t="kv-cache">the KV cache</Term>. Each step reads them back from memory (blue) and computes exactly one new token (green). Same answer, 115× less arithmetic, and the work is now linear in the output length.
  </Step>

## Then derive it properly

### The unit of work: a token-forward

From Module 02: a forward pass over a sequence of *m* tokens costs $F = 2 m P$ FLOPs, where $P$ is the parameter count — every weight touched once per token, two FLOPs per multiply-add. So the natural unit of work is the **token-forward**: one token pushed through the whole model.

$$
F = 2 P m \qquad [\text{FLOPs}]
$$

A token-forward for Llama-3.1-8B has $P = 8.03 \times 10^{9}$, so $F = 2P \approx 16.1$ GFLOP. That is the atom. Everything below counts atoms.

### Counting the naive loop

With a prompt of $p$ tokens and $n$ tokens to generate, a naive generator does step $i = 0, 1, \ldots, n-1$ on a sequence of $p + i$ tokens:

$$
W_{\text{naive}} = \sum_{i=0}^{n-1} (p + i) = n p + \frac{n(n-1)}{2}
$$

The cache version processes the prompt once and then one token per step:

$$
W_{\text{cached}} = p + n
$$

<Callout type="math" title="Worked example: 512-token prompt, 128 tokens out, Llama-3.1-8B">
  $$
  W_{\text{naive}} = 128 \times 512 + \frac{128 \times 127}{2} = 65{,}536 + 8{,}128 = 73{,}664
  $$

  $$
  W_{\text{cached}} = 512 + 128 = 640
  $$

  Ratio $= 73{,}664 / 640 = 115$. Waste $= 1 - 640/73{,}664 = 99.13\%$.

  As FLOPs: $W_{\text{naive}} \times 16.1 \approx 1.19 \times 10^{15}$, or **1.19 PFLOP thrown away** to write a short paragraph.
</Callout>

There is a cleaner way to say the same thing, and it is the one you will use when reasoning about your own service. Divide the naive total by the tokens generated:

$$
\frac{W_{\text{naive}}}{n} = p + \frac{n-1}{2}
$$

**You spend one token-forward for every token of *average* context length, to produce one token.** With a 512-token prompt and 128 output tokens that is 512 + 63.5 = **576 token-forwards per output token**. With a 32K context it is over 32,000. The cache makes the number exactly 1.

| Prompt $p$ | Output $n$ | Naive token-forwards | Needed | Ratio | Wasted |
|---|---|---|---|---|---|
| 128 | 64 | 10,208 | 192 | 53× | 98.1% |
| 512 | 128 | 73,664 | 640 | 115× | 99.1% |
| 1,024 | 256 | 294,784 | 1,280 | 230× | 99.6% |
| 4,096 | 512 | 2,227,968 | 4,608 | 484× | 99.8% |

The growth is the real story. With $p = 4n$ — a prompt four times the length of the answer, which is typical — the naive cost is about $n \cdot p + n^2/2 \approx 4.5 n^2$ token-forwards, and the ratio grows **linearly with the output length**. Double the answer and you double the waste. There is no length at which this becomes acceptable.

```python
def forwards_naive(p, n):
    """Token-forwards a recomputing generator does."""
    return sum(p + i for i in range(n))      # n*p + n(n-1)/2

def forwards_cached(p, n):
    """Token-forwards a generator with a KV cache does."""
    return p + n                              # the prompt once, one token per step

for p, n in [(128, 64), (512, 128), (1024, 256), (4096, 512)]:
    a, c = forwards_naive(p, n), forwards_cached(p, n)
    print(f"p={p:>5} n={n:>4}  naive={a:>9,}  cached={c:>7,}  {a/c:6.0f}x  waste {100*(1-c/a):5.1f}%")
```

### Why 99% wasted arithmetic is not 99% wasted time

This is the part that surprises everyone, and it falls straight out of Module 02's roofline.

A <Term t="memory-bound">memory-bound</Term> decode step is waiting on the memory system, with the tensor cores **idle**. Feeding that idle machine a hundred times more arithmetic is nearly free in wall-clock terms. So the honest comparison on one H100 is not "115× slower" — it is about **2.2× slower** for a 128-token answer, and about 6× for a 2,048-token answer.

Look at the wall-clock line in the readout above the diagram. Two seconds instead of one, for the same 128 tokens. Why so tame?

<Callout type="intuition" title="Waste only costs what it is made of">
  FLOPs and bytes are different currencies, bought at very different exchange rates. A recomputing generator spends the currency the machine has in surplus (arithmetic) and keeps the one it is short of (bandwidth). That is why 99% of the FLOPs can be worth 50% of the time.

  The rule generalises: **an optimization is only worth what it saves in the scarce resource.** On a memory-bound workload, cutting bytes is worth far more than cutting FLOPs. On a compute-bound one, the reverse.
</Callout>

Recomputation is not free. It is merely paying in the wrong currency. And there are three places where the bill arrives anyway.

<Callout type="pitfall" title="The three places the waste really bites">
  **1. Long answers.** The ratio grows linearly in $n$. At 2,048 output tokens you are 6× slower; at 8,192, about 18×. The quadratic term $n(n-1)/2$ does not care how fast the GPU is.

  **2. Batching — the killer.** Without a cache you cannot amortise anything. A batch of 32 conversations is 32 independent quadratic recomputations, so serving 32 users costs 32× the work instead of sharing one read of the weights. Throughput per GPU collapses, and cost per token explodes. This is why no serving engine offers it.

  **3. Long context.** Once the conversation is long enough that the KV history outweighs the model, *reading* that history is the bottleneck instead. A generator that re-derives it from scratch must also write all of it again on every step, so the memory traffic is quadratic too.
</Callout>

### The loop you will see in real code

Here is the naive generator, spelled out. It is four lines, and it is exactly the shape of code that gets shipped by accident.

```python
ids = tokenizer(prompt, return_tensors="pt").input_ids
generated = []
for _ in range(max_new_tokens):
    logits = model(input_ids=ids).logits       # the WHOLE sequence, every call
    nxt = int(logits[0, -1].argmax())
    generated.append(nxt)
    ids = torch.cat([ids, torch.tensor([[nxt]])])   # next call recomputes all of it
```

It is not hypothetical. `model.generate(..., use_cache=False)` in HuggingFace Transformers does precisely this, and it is a real option on the `generate` API because it is the honest reference implementation: no cache, no bugs, easy to check. It is how you measure what the cache is worth. It is not how you serve anyone.

<Callout type="real" title="Why the cache is the substrate, not an optimization">
  The KV cache is usually taught as a constant-factor speedup, and that undersells it. Once old keys and values live outside the model, several things that are otherwise impossible become routine:

  - **Batching.** One forward pass serves every sequence in the batch, because each sequence only needs its own new row computed.
  - **Prefix sharing.** Two requests with the same system prompt can share one set of cached keys and values (Module 10).
  - **Paged storage.** The cache becomes a block allocator you can page in and out of a pool (Module 08).
  - **Disaggregation.** Prefill on one GPU, decode on another, moving the cache between them (Module 21).
  - **Speculation.** A draft model proposes several tokens; the target model verifies them all in one pass over the shared cache (Module 16).

  Every one of those is a Module 05 idea wearing a later module's clothes. This is the foundation.
</Callout>

<Callout type="mentor">
  When you profile a slow decode loop, check for this before anything clever: is the same prefix being re-processed every step? The symptom is a step time that *grows with the output length* — a clean, unmistakable signature, because a cached decode step is nearly independent of how many tokens came before.
</Callout>

## What the fix has to cost

Everything in engineering is a trade. A cache is memory that is set aside, and it is written to once per generated token. Before Module 05 ends you will have computed exactly how much: **128 KB per token for Llama-3.1-8B in BF16**, 1 GB for an 8,192-token conversation, and a hard ceiling on how many conversations fit on one GPU. That ceiling, not the arithmetic, is what limits a real service.

The next lesson builds the cache. Then we separate the two phases of a request, because they are different workloads that want opposite things from the hardware.

<KeyNotes>
  1. A model emits **one token per forward pass**, and each new token is fed back in. That is autoregressive generation.
  2. Count work in **token-forwards**: one token through the whole model, worth $F = 2P$ FLOPs. 16.1 GFLOP each for Llama-3.1-8B.
  3. A naive generator does $np + n(n-1)/2$ token-forwards. A cached one does $p + n$. For a 512-token prompt and 128 output tokens that is 73,664 against 640: **99.1% waste**.
  4. Equivalently: a naive generator spends **one token-forward per token of average context** to produce one token. 576 forwards per token at p = 512, n = 128.
  5. Waste is *quadratic* in the output length, so the ratio grows linearly. There is no answer length at which recomputing becomes acceptable.
  6. 99% wasted FLOPs is only about 2.2× wasted time on an H100, because decode is memory-bound and the tensor cores are idle. **Waste costs what it is made of** — spend the surplus resource, not the scarce one.
  7. The waste becomes expensive where the arithmetic is the scarce resource: long answers, any form of batching, and long context where KV traffic exceeds weight traffic.
  8. `use_cache=False` is the reference implementation of this loop. Useful for measuring the cache's value, wrong for serving.
</KeyNotes>
