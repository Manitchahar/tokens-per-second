## Half one: the simulator

Four implementations, one layer of Llama-3.1-8B. Change the **phase** (prefill or decode), the **context length**, the **backend**, and the **GPU**, and watch four things move together: peak extra memory, memory traffic, which speed limit the layer hits, and the resulting time.

The whole point is the *shape* of the curves. Slide context up and watch eager's memory bar grow quadratically while fused stays flat. Switch to decode and the whole picture inverts.

  <Step title="1. Four implementations, one workload">
    Only the kernel changes between these four bars. Same model, same layer, same GPU. Everything on screen is computed from that GPU's bandwidth and FLOP/s — no benchmark is being run, so what you see is a prediction you will test in the notebook.
  </Step>

  <Step title="2. Eager pays for the intermediate">
    At 4,096 tokens eager holds both the $T \times T$ score matrix and its normalised copy. Over 2 GB of extra memory for a single layer. Set the GPU to T4 and push the context past 8K and you can watch it cross that card's 16 GB of memory.
  </Step>

  <Step title="3. FlashAttention removes it">
    Switch to FlashAttention and the memory bar collapses to about 45 KB. **It does not change as you raise the context**, because the peak is now dominated by the tiles in SRAM, not by the sequence.
  </Step>

  <Step title="4. The causal mask is free speed">
    The schematic on the left shows the triangular tiles. Roughly half the score matrix is masked, and a good kernel never computes it. That is a constant-factor FLOP saving you get whether or not the kernel is fused.
  </Step>

  <Step title="5. Decode is a different shape">
    Switch the phase to decode. The schematic collapses to a single query row against the whole cache, and eager's memory advantage evaporates — there is no big intermediate to pay for, because there is only one query.
  </Step>

  <Step title="6. Split-K fills the machine">
    In decode, all backends are memory-bound and the only lever is getting more SMs busy. FlashDecoding splits the sequence across them. The saving is smaller than in prefill because you are fighting bandwidth either way.
  </Step>

  <Step title="7. Paged reads scattered blocks">
    The paged kernel gathers through a block table, costing about 1% extra traffic. It is not free, but it is small — and it buys something memory management cares about more than this kernel does.
  </Step>

  <Step title="8. Pick by shape, not by name">
    Change the GPU. A compute-bound phase scales with FLOP/s; a memory-bound phase scales with bandwidth. Change the context. The best backend in prefill is rarely the best one in decode. **This is why backend choice is a measurement, not a preference.**
  </Step>
</Scrolly>

### 1. Prove the online softmax on the CPU

Before touching the GPU, section 1 checks the mathematics. It implements the online update from lesson 1 — merge running maximum, sum and output across tiles — and compares it against a plain two-pass softmax on random data.

**Expected output:** the two agree to within float32 rounding, around 1e-6, and the row sums are 1. If they disagree in a way that grows with the number of tiles, your merge is wrong, not the reference.

Do not skip this cell. Every kernel below is a faster way of running this exact update, and if the update is wrong everything downstream is wrong in a subtle way.

### 2. Watch eager attention's memory blow up

Section 2 runs plain `softmax(QKᵀ)V` on a real layer shape while tracking `torch.cuda.max_memory_allocated`. It sweeps context from 512 to 4,096 tokens and prints peak memory per layer.

**What to expect.** Peak memory roughly quadruples every time you double the context — that is the $T^2$. And at 4,096 tokens on a T4, one layer of Llama-3.1-8B in BF16 already sits above what the card comfortably holds once you account for Q, K, V and O. This is the failure the whole module exists to remove.

### 3. Write a fused Triton kernel and verify it

Section 3 is the real work: a FlashAttention forward kernel in Triton, built exactly like the one in the lesson — Q tile held in registers, loop over key tiles, online softmax inside, one division at the end.

Then it checks correctness. **This is the important part.** It compares the fused output against PyTorch's reference on the same inputs and prints the maximum absolute difference.

**Expected output:** a max difference well under 1e-2 in BF16 (which has only three decimal digits, so this is rounding, not error) and the fraction of elements matching at that tolerance essentially 1.0. If the difference is large, the usual culprits are: forgetting the `1/sqrt(d)` scale, not masking the causal half, or initialising the running maximum to something other than `-inf`.

### 4. Sweep the tile size

Section 4 times the fused kernel across `BR = 32, 64, 128` at a fixed context, and against eager at the same context.

**What to expect.** Fused beats eager everywhere at 4,096 tokens, by roughly the ratio your simulator predicted. Tile size matters but not enormously — the win is fusion, not the specific tile. You should also see 128 sometimes tie 64: larger tiles use more registers and can cost occupancy, which is the trade the lesson warned about.

### 5. Decode: confirm the bandwidth wall

Section 5 switches to decode — a single query row against the whole cache — and measures achieved bandwidth and FLOP/s for both a prefill-shaped and a decode-shaped call at long context.

**The check that matters.** Compute the intensity yourself and compare it to the roofline. For this model decode intensity is the GQA group factor, a handful of FLOP per byte, and the achieved GB/s should sit near the T4's peak (about 320 GB/s) while TFLOP/s is nearly zero. **If you see high FLOP/s in decode, you have a bug — you are probably not actually running the 1-query case.**

### 6. Split-K decode, and the combine

Section 6 implements FlashDecoding: split the sequence, reduce each split to a partial $(m, \ell, O)$, and merge with the online-softmax rule.

**Expected:** the merged result matches the unsplit decode to within float32 rounding, and at small batch the split version is faster because it uses more SMs. At large batch the split stops helping — the machine is already full and you are paying combine overhead for nothing.

That crossover is the single most useful number in the notebook, because it is the "when does decode split-K help" answer for your GPU specifically.

### 7. A paged attention kernel, verified

Section 7 scatters a real KV tensor into blocks, computes attention through the block table, and checks it against the contiguous version.

**Expected:** `allclose: True`, and a max difference at rounding level. Then it times paged against contiguous and prints the overhead percentage. On a T4 the KV is small, so the gather is latency-bound rather than bandwidth-bound — expect an overhead that looks larger than the theoretical ~1% and gets closer to it as you raise the context. That is a real effect, not an error.

### 8. Put it in the model

Section 8 loads Qwen2.5-0.5B-Instruct, runs a short generation, and — the useful part — times the model's real attention path. It prints the KV bytes per token straight from the model config so you can check it against the constant you have been using.

**Expected:** bytes/token matches your hand calculation for that architecture. If it does not, `num_key_value_heads` is the field that will explain it.

### 9. When it goes wrong

Four ways a fused attention kernel produces wrong answers instead of crashing:

**Forgotten scale.** Dropping the `1/sqrt(d)`. Symptoms: output that is superficially plausible but noticeably worse; no NaNs.

**Missing causal mask.** Forgetting to mask the future half. In decode (where the query is one row of length $T$) this leaks nothing that looks obviously wrong, so it survives tests — but in a model it quietly breaks causality. One fix: assert that positions after the diagonal are `-inf` before the max.

**Running max initialised to 0, not `-inf`.** The subtle one. If every real maximum is positive the numbers are fine, so it passes normal tests; on a batch where some rows' scores are all negative it over-counts and the row stops summing to 1. Fix: initialise to `-inf`, and the first correction `exp(-inf - m)` is 0, cleanly discarding the empty state.

**Accumulator left in BF16.** Keeping the running `acc` in low precision across thousands of tiles accumulates rounding error that looks like a quality regression, not a numerical bug. Fix: keep the accumulator (and `m`, `l`) in FP32 even when Q/K/V are BF16. This one costs almost nothing and is the single most common precision mistake in hand-written kernels.

<Callout type="mentor" title="The habit this lab is really building">
  Every cell follows the same order: **implement, verify, then time.** Not time, then verify. Timing a kernel you have not checked produces a number you will confidently report and that will be wrong.

  This is the same discipline as Module 06's reproducible benchmarks, applied to kernels. When a fused kernel disagrees with a reference, the first question is never "how much faster is it" — it is "is it correct".
</Callout>

## Check yourself

Answer these in your notes, with the arithmetic shown.

1. Section 2 quadruples context and you see peak memory roughly quadruple. Derive that from the shape of the score matrix, not from the measurement.
2. Section 4 shows `BR=128` is not always faster than `BR=64`. Give the hardware reason.
3. Section 5's decode intensity is 4 FLOP/byte. Compute the predicted time for a 32-layer layer reading 8,192 tokens of KV on a T4 (320 GB/s) and compare to what you measured.
4. Section 6's split-K helps at batch 1 and stops helping at batch 64. In one sentence, why?
5. From the whole lab: which single change gave the biggest measured win — fusion, tile size, or split-K — and what does that tell you about where to spend effort next?

**Answers, once you have done the work:**

1. The score matrix is $T \times T$, so it holds $T^2$ numbers; doubling $T$ gives four times the numbers and four times the bytes. The KV tensors around it are linear in $T$, so the quadratic term dominates at long context.
2. Larger query tiles mean fewer loop iterations and better tensor-core utilisation, but they need more registers to hold the accumulator (`BR x D`) and the score tile. Past a point the extra register pressure cuts occupancy — fewer resident blocks per SM — and the lost parallelism outweighs the better per-block efficiency.
3. Bytes = 8,192 tokens × 131,072 bytes/token = 1.07 GB (for Llama-3.1-8B; use the KV bytes/token from section 8 for your actual model). At 320 GB/s that is about 3.4 ms for all 32 layers of KV traffic alone. Your measured decode time will be longer, because weights and the rest of the layer are in there too — but the attention share should be consistent with this floor.
4. Split-K's whole purpose is to give idle SMs something to do. At batch 1 there are only one query row's worth of parallelism, so splitting helps enormously; at batch 64 the machine is already saturated by the batch, so splitting adds combine overhead and parallel work without adding throughput.
5. Fusion gave the biggest win by far, because it removed an $O(T^2)$ term that everything else merely worked around. The lesson: attack the term that grows fastest with the parameter that matters, not the one that is easiest to tune.

<KeyNotes>
  1. Implement, verify, then time — in that order. A speed number for an unverified kernel is a number you will confidently report and that will be wrong.
  2. The online softmax on the CPU must match a two-pass reference before you fuse it into anything. Every fast kernel below is a faster way of running that one update.
  3. Eager attention's peak memory grows as $T^2$; fused attention's peak is $O(B_r d + B_c d)$ and is flat in context. That flatness is the property long-context prefill depends on.
  4. Fused beats eager at long context by roughly the ratio of the traffic you removed, and the tile size (`BR`) is a second-order knob that register pressure can turn around.
  5. Decode should show near-peak GB/s and near-zero TFLOP/s. High FLOP/s in a decode-shaped call means the call is not actually decode-shaped.
  6. Split-K's crossover point — where extra splits stop helping because the batch already saturates the machine — is a per-GPU number worth recording for your workload.
  7. A paged kernel's gather shows up as a latency-bound overhead on small KV and approaches the bandwidth-bound figure (~1%) as context grows. Both are correct; the apparent gap is a cache effect.
  8. Keep the accumulator, `m` and `l` in FP32 even when Q/K/V are BF16. Accumulating rounding across thousands of tiles looks like a quality regression, not a bug, which is why it is dangerous.
</KeyNotes>
