Imagine you run a summarisation API for forty companies. Full fine-tuning gives you forty models, which means forty times the weights, forty GPUs, and a bill you cannot defend to a finance team. The obvious fix — a smaller base model — costs you quality on exactly the domain your customers pay for.

The <Term t="lora">LoRA</Term> answer is that the specialists are tiny. Each one is under half a percent of the base model, so you load one base once and swap a 65 MB file per request. The arithmetic that makes this work is small, and this lesson is mostly about doing it properly — and about the one cost that does not show up in the parameter count.

## A low-rank correction

LoRA's observation is that a fine-tuned model's *update* to the original weights is low-rank. Not the weights themselves — those are full-rank — but the delta $\Delta W$ that fine-tuning adds.

The trick is to never materialise $\Delta W$. Instead of learning an $(out \times in)$ matrix, learn two thin ones:

$$
W' = W_0 + \Delta W = W_0 + BA, \qquad A \in \mathbb{R}^{r \times in}, \quad B \in \mathbb{R}^{out \times r}
$$

The base $W_0$ stays frozen. Only $A$ and $B$ train. The rank $r$ is the knob: $r = 0$ is the base model exactly, and $r \geq \min(in, out)$ can express any update at all.

<Callout type="intuition" title="Why low rank is a reasonable bet">
  A fine-tune usually changes a model's *style and behaviour* far more than its knowledge. Style is a low-dimensional shift; knowledge is high-dimensional. So the useful part of a fine-tune tends to live in a small number of directions, and a rank-16 update has enough room to capture it. That is an empirical observation, not a theorem — but it is why $r$ in the single digits to low tens works so widely.
</Callout>

## The parameter arithmetic

This is the whole economics, so let me derive it rather than quote it.

For a matrix of shape $(out, in)$, the base holds $in \cdot out$ parameters. The adapter holds:

$$
\underbrace{r \cdot in}_{A} + \underbrace{out \cdot r}_{B} = \boxed{r(in + out)}
$$

Take Llama-3.1-8B: 32 blocks, hidden width $d = 4096$, intermediate 14336, and GQA with 8 KV heads of 128 dims so the key and value projections are 1024 wide rather than 4096.

One attention projection, 4096 × 4096, at $r = 16$:

$$
r(d + d) = 16 \times 8192 = 131{,}072 \text{ parameters}
$$

$$
\text{share of the matrix it modifies} = \frac{131{,}072}{16{,}777{,}216} = \boxed{0.78\%}
$$

Now scale to the whole model. Adapting all four attention projections in every block:

$$
32 \times 2 \times \underbrace{r(d+d)}_{q,o} + 32 \times 2 \times \underbrace{r(1024 + d)}_{k,v}
= 32 \times 2 \times 16 \times 8192 + 32 \times 2 \times 16 \times 5120
$$

$$
= 8{,}388{,}608 + 5{,}242{,}880 = \boxed{13.6\text{M}}
$$

And the feed-forward pair, which is where the parameters actually are:

$$
32 \times \Big(r(14336 + 4096) + r(4096 + 14336)\Big) = 32 \times 2 \times 16 \times 18432 = \boxed{18.9\text{M}}
$$

Together:

$$
13.6\text{M} + 18.9\text{M} = 32.5\text{M}, \qquad \frac{32.5\text{M}}{8.03\text{B}} = \boxed{0.41\%}
$$

<Callout type="math" title="Why rank is quoted against hidden width">
  People say "rank 16 on a 4096-wide model", and the shorthand $r/d$ is not the real ratio. The real ratio is $r(in+out)/(in \cdot out)$, which for a square matrix is $2r/d$ — twice the shorthand. It matters because the shorthand makes rank look cheaper than it is. For a rectangular matrix like the feed-forward up-projection it is worse still: $r(14336+4096)/(14336 \cdot 4096)$ is $3r/14336$, about a quarter of $r/d$.

  **Compute $r(in+out)/(in\cdot out)$, always.** The shorthand is a label, not a measurement.
</Callout>

Here is the whole table, so you can see how each knob moves:

| rank $r$ | attention only | + feed-forward | share of base | size at BF16 |
|---|---|---|---|---|
| 1 | 0.85M | 2.0M | 0.025% | 4 MB |
| 4 | 3.4M | 8.1M | 0.101% | 16 MB |
| 8 | 6.8M | 16.3M | 0.202% | 33 MB |
| **16** | **13.6M** | **32.5M** | **0.405%** | **65 MB** |
| 32 | 27.3M | 65.0M | 0.810% | 130 MB |
| 64 | 54.5M | 130M | 1.619% | 260 MB |

Linear in $r$, as it must be. Which rank you need is an evaluation question, not an arithmetic one — but the table tells you what each choice costs before you run the evaluation.

## The memory of a fleet

Now the deployment question. You can serve any adapter that is resident, and you cannot know which one the next request needs, so **every adapter you might serve must be loaded**. Total memory is:

$$
M_{\text{total}} = \underbrace{P_{\text{base}} \cdot b}_{\text{base}} + \underbrace{N \cdot P_{\text{lora}} \cdot b}_{\text{adapters}}
$$

For Llama-3.1-8B at BF16 on an A100 (80 GB):

| adapters | base | adapters | total | base share |
|---|---|---|---|---|
| 1 | 16.06 GB | 0.07 GB | 16.13 GB | 99.6% |
| 8 | 16.06 GB | 0.52 GB | 16.58 GB | 96.9% |
| 16 | 16.06 GB | 1.04 GB | 17.10 GB | 93.9% |
| 32 | 16.06 GB | 2.08 GB | 18.14 GB | 88.5% |
| 64 | 16.06 GB | 4.16 GB | 20.22 GB | 79.4% |

Read the last column. Even at 64 adapters, nearly four fifths of the memory is the base model. **The marginal cost of a tenant is tens of megabytes.** Compare that to 16 GB — the cost of a second full replica — and the argument is finished.

<Callout type="real" title="What this actually replaces">
  Multi-LoRA exists because it turns "N models" into "1 model + N small files". The alternative for forty tenants is either forty replicas (forty times the memory, forty times the cold-start cost, forty times the operational surface) or one mediocre multi-tenant model (no specialisation at all). The base-share column is the number that makes the trade obvious.
</Callout>

### Adapters can be quantized too

An adapter is a tiny, well-conditioned set of matrices, so 8-bit or even 4-bit adapters work well — and this multiplies the fleet size you can serve. Holding the base at BF16 and shrinking only the adapters:

| adapters | adapter precision | adapters' bytes | total | fleets per A100 |
|---|---|---|---|---|
| 64 | BF16 | 4.16 GB | 20.22 GB | 3 |
| 64 | 4-bit | 1.04 GB | 17.10 GB | 4 |
| 128 | 4-bit | 2.08 GB | 18.14 GB | 4 |

Note the ceiling: even at 128 four-bit adapters the total is still dominated by the 16 GB base, and the number of complete fleets you can hold barely moves. **Adapters are so cheap that quantizing them buys you tenants, not capacity.** To hold genuinely more tenants you quantize the *base* too — which is Module 11's quantization applied to a workload where one set of weights is shared by everyone.

## The cost nobody budgets: batch mixing

Memory is the number everyone calculates. This is the one they forget.

In a serving engine a decode step reads the weights once for the whole batch (Module 05). If all 32 sequences in the batch want the same adapter, that is one ordinary GEMM with 32 rows — optimal, memory-bound, exactly the shape you tuned for in Modules 06 and 09.

Now suppose those 32 sequences belong to four different tenants. The engine must group the rows by adapter:

| adapters in the batch | rows per GEMM | slowdown |
|---|---|---|
| 1 | 32 | 1.00× |
| 2 | 16 | 1.06× |
| 4 | 8 | 1.21× |
| 8 | 4 | 1.47× |
| 16 | 2 | 1.96× |

The mechanism: memory-bound GEMMs get their bandwidth utilisation from having enough rows to saturate every memory transaction. Below roughly 8–16 rows the kernel starts leaving bandwidth idle, and the step slows down even though it moves exactly the same bytes.

<Callout type="pitfall" title="Adapter count and batch size are the same dial">
  This is the trade nobody puts in a slide. Spreading a fixed batch across many adapters is *exactly* equivalent to shrinking the batch, because the weight read is per-GEMM and you now pay it four times instead of once. **If you have 100 tenants, serving 4 concurrently per step is the same as serving 16 tenants at batch 4.**

  The mitigations are all routing decisions: group requests by adapter (cache-aware routing, Module 23), size the engine so each adapter's concurrency is reasonable, or accept a larger adapter footprint to keep batches dense.
</Callout>

<Callout type="intuition" title="Why this compounds with prefix caching">
  There is a helpful interaction. Requests for the same adapter are also likely to share a system prompt, so they hit the same prefix cache (Module 10). That both cuts prefill and makes affinity routing doubly valuable: **sending a request to the replica that already has its adapter *and* its prefix cached is the single biggest latency win available in a multi-adapter deployment.**
</Callout>

## Choosing the configuration

If you are deploying this, the decisions in order:

| decision | default | when to change |
|---|---|---|
| target matrices | attention + FFN | attention-only if memory-bound and the task is format/style |
| rank $r$ | 16 | 8 for pure style, 32–64 for new capability |
| adapter precision | 8-bit | 4-bit when fleet size is the constraint |
| base precision | BF16 or FP8 | 4-bit only if you have measured the quality cost (Module 11) |
| batching | group by adapter | only when adapter count per batch is small |

The most common production mistake is choosing $r$ by what the memory budget allows rather than by what the task needs. Rank is a *modelling* decision made in evaluation; the memory consequence is secondary and, as the table above shows, tiny.

```python
# The whole serving contract: one base, N adapters, swap per request.
class MultiLoRAServer:
    def __init__(self, base_path, adapter_dir):
        self.base = load_model(base_path)              # loaded once
        self.adapters = {
            name: load_lora(path)                     # rank r, small
            for name, path in list_adapters(adapter_dir)
        }

    def generate(self, tenant: str, prompt: str) -> str:
        # Attach this tenant's adapter, generate, detach. The base is untouched.
        with self.base.use_adapter(self.adapters[tenant]):
            return self.base.generate(prompt)

    def prefill_estimate(self, tenant: str, prompt_tokens: int) -> float:
        # Identical for every tenant: the adapter does not change prefill FLOPs.
        # It changes decode quality, not decode cost.
        return 2 * BASE_PARAMS * prompt_tokens / (GPU_FLOPS * MFU)
```

That last method is worth pausing on, because it is true and it surprises people: **a LoRA adapter does not make generation faster or slower in any way the decode-step model can see.** It adds $r(in+out)$ multiply-accumulates per adapted matrix — vanishing next to reading the base weights — and it changes what the model *says*. Adapter latency is a memory-footprint and batching question, not an arithmetic-intensity question.

<KeyNotes>
  1. LoRA learns a rank-$r$ update $BA$ rather than a full $\Delta W$, so an adapter on an $(out \times in)$ matrix holds exactly $r(in + out)$ parameters.
  2. For Llama-3.1-8B, a rank-16 adapter over all attention and feed-forward projections is 32.5M parameters — **0.41% of the base**, 65 MB at BF16.
  3. The real ratio is $r(in+out)/(in\cdot out)$, which for a square matrix is $2r/d$ — twice the usual $r/d$ shorthand. The shorthand is a label, not a measurement.
  4. Serving $N$ adapters costs $P_{base} \cdot b + N \cdot P_{lora} \cdot b$. At 64 rank-16 adapters the base is still 79% of memory, so a tenant costs tens of megabytes instead of 16 GB.
  5. Adapters quantize well, so 4-bit or 8-bit adapters multiply the fleet size you can hold — a global win, since quantizing the base affects every tenant equally.
  6. The cost that is easy to miss is batch mixing: rows must be grouped by adapter into separate GEMMs, and a GEMM of 2–4 rows wastes bandwidth, so spreading a batch across tenants is equivalent to shrinking the batch.
  7. Adapter count per step and batch size are the same dial. If you have 100 tenants at batch 32, you are running batch 4 with four weight reads — group by adapter or shrink the fleet.
  8. A LoRA adapter adds $r(in+out)$ FLOPs per adapted matrix, which is negligible against reading the base weights. Adapter latency is a memory and batching question, not an arithmetic-intensity one.
</KeyNotes>
