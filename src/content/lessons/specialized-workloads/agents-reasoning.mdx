A customer asks a question. The model answers. They ask a follow-up. From the engine's point of view this is a brand-new request: prefill the whole conversation, decode a reply.

But look at what the second request actually contains. It is the *first request*, byte for byte, followed by some new tokens. The model computed the answer to the first question, then threw that computation away and paid to recompute it.

Nothing about multi-turn chat is new. It is Module 10's prefix caching applied to a workload that repeats itself perfectly.

## Turn two is turn one, again

Take a concrete conversation: an 800-token system prompt, and roughly 120–160 tokens per turn. Walk the context:

| turn | context before | added | context after | cached blocks | fresh blocks |
|---|---|---|---|---|---|
| 1 | 800 | 160 | 960 | 50 | 10 |
| 2 | 960 | 120 | 1,080 | 60 | 8 |
| 3 | 1,080 | 160 | 1,240 | 68 | 10 |
| 4 | 1,240 | 120 | 1,360 | 78 | 7 |
| 5 | 1,360 | 160 | 1,520 | 85 | 10 |
| 6 | 1,520 | 120 | 1,640 | 95 | 8 |

The second column that matters is the last one. With a 16-token block size, turn 6 reuses 95 blocks and computes 8. **About 92% of that turn's prefix is already sitting in the cache.**

Now count the prefill work. Without a cache, each turn prefills its entire context:

$$
960 + 1080 + 1240 + 1360 + 1520 + 1640 = \boxed{7{,}800 \text{ token-prefills}}
$$

With a perfect prefix cache, only the new tokens are computed:

$$
160 + 120 + 160 + 120 + 160 + 120 = \boxed{840}
$$

$$
\text{saved} = 1 - \frac{840}{7800} = \boxed{89\%}
$$

In FLOPs on an 8B model: 125 TFLOP becomes 13.4 TFLOP. **The cache removes nine tenths of the prefill work in an ordinary conversation.**

<Callout type="intuition" title="Why this is a stronger cache hit than any chat workload">
  Most production traffic has low prefix reuse — every user sends something different. A conversation has *perfect* reuse: every turn extends the previous prefix and changes nothing before it. It is the best possible case for prefix caching, and a production system serving chat should assume it is getting it.
</Callout>

  </Step>

## The agent loop, and why it is quadratic

An agent is this conversation with a tool call in the middle. The user asks, the model calls a tool, the tool returns something, the model reads it and calls another tool. Each observation appends to the context.

Let 3,000 tokens be a realistic tool result — a file read, a search, a database page. Starting from an 800-token system prompt:

| turn | context | new tokens | cumulative prefill (with cache) | without cache |
|---|---|---|---|---|
| 1 | 3,800 | 3,000 | 3,000 | 3,800 |
| 2 | 6,800 | 3,000 | 6,000 | 10,600 |
| 3 | 9,800 | 3,000 | 9,000 | 20,400 |
| 4 | 12,800 | 3,000 | 12,000 | 33,200 |
| 8 | 24,800 | 3,000 | 24,000 | **114,400** |
| 20 | 60,800 | 3,000 | 60,000 | **646,000** |

Without reuse, turn $t$ prefills the whole context, so the total is:

$$
\sum_{t=1}^{T}(s + t \cdot o) = Ts + o\frac{T(T+1)}{2} = \boxed{O(T^2)}
$$

With a perfect prefix cache it is just $T \cdot o$ — **linear**. At 20 turns the gap is 646,000 versus 60,000 tokens, a factor of **10.8**.

<Callout type="math" title="Why the quadratic term hurts more as context grows">
  The ratio is $\dfrac{Ts + o\frac{T(T+1)}{2}}{o \cdot T} = \dfrac{s}{o} + \dfrac{T+1}{2} \approx \dfrac{T}{2} + \dfrac{s}{o}$. It does not depend on the model, the GPU, or the framework — it is pure bookkeeping.

  So the cost of not caching an agent loop is **about $T/2$**. Ten turns, ~6× the necessary prefill. Twenty turns, ~11×. Any agent framework that ships without prefix caching for a 20-turn loop has a performance bug, not a tuning problem.
</Callout>

Note the shape of the fix. Because turn $t$ only ever *appends*, the entire prefix from turn $t-1$ is still valid. This is the ideal case for a <Term t="prefix-caching">prefix cache</Term> — but it requires that the observation be appended verbatim and that the system prompt be *bit-identical* across turns.

<Callout type="pitfall" title="What silently destroys your cache hit rate">
  Three things, all common:

  1. **A timestamp or request ID in the system prompt.** Now every request has a unique prefix and the cache never hits. This is the single most common cause of "we enabled prefix caching and saw no improvement".
  2. **A non-deterministic tool result in the prefix** — a random ID, a live clock, a shuffled list.
  3. **Swapping adapters mid-conversation**, which changes the weights and invalidates every cached block (Module 10's routing lesson again).

  Fix these before tuning anything else. A 0% hit rate cannot be improved by a better eviction policy.
</Callout>

## Reasoning models: more tokens, same loop

A reasoning model emits explicit deliberation before answering. The engineering consequence is not new machinery — it is that **the answer is 5,000 tokens instead of 200.**

There is a second-order effect that is easy to miss and expensive: **the trace joins the context.** Turn 2 of a reasoning conversation carries turn 1's entire deliberation.

Let me quantify the self-slowing. Decode is memory-bound. At step $t$ the step reads the weights once for the whole batch, plus the KV for the $t$ tokens already generated. Per token:

$$
\text{bytes}(t) = \frac{w}{B} + t \cdot kv
$$

Note the $w/B$. The weight set is read once per step, not once per token, so in a batch of $B$ sequences each token only pays ${}1/B$ of the weight read. The KV term, by contrast, is genuinely per token.

The total time to emit a trace of length $T$ is therefore an **integral**, not a mean times a count:

$$
t_{\text{total}} = \sum_{t=1}^{T} \frac{w/B + t\,kv}{\text{BW}\cdot\text{MBU}} = \boxed{\frac{wT/B + kv\,T^{2}/2}{\text{BW}\cdot\text{MBU}}}
$$

<Callout type="pitfall" title="The factor-of-two that makes traces look faster than they are">
  Evaluating at the *mean* context ($kv \cdot T/2$) instead of integrating halves the KV term. Since the KV term dominates for long traces, the naive estimate is off by nearly 2× — and always in the flattering direction. Long-context work (Module 20) and reasoning models both hit this, which is why this course keeps returning to integration rather than averages.
</Callout>

With an 8B model in BF16 on an H100 (3.35 TB/s, 128 KB KV per token, 85% of peak bandwidth):

| trace length | at batch 32: bytes/token | speed at the end | total time |
|---|---|---|---|
| 200 | 528 MB | 5,392 tok/s | 0.04 s |
| 1,200 | 659 MB | 4,320 tok/s | 0.24 s |
| 5,000 | 1,157 MB | 2,461 tok/s | 1.5 s |
| 16,000 | 2,599 MB | 1,096 tok/s | 8.7 s |

Going from a 200-token answer to a 16,000-token trace makes the final tokens **4.9× slower**, and the total time 200× worse. But look at the batch column, because it is the real lesson:

| batch | speed at 200 tokens | speed at 16,000 tokens | 16k trace takes |
|---|---|---|---|
| 1 | 177 tok/s | 157 tok/s | 96 s |
| 8 | 1,400 tok/s | 694 tok/s | 17 s |
| 32 | 5,392 tok/s | 1,096 tok/s | 8.7 s |
| 64 | 10,274 tok/s | 1,213 tok/s | 7.3 s |

<Callout type="intuition" title="Why batch 1 is a trap and batch 32 is the answer">
  At batch 1 the weight read is 16 GB for a single token, so throughput is pinned near 160 tok/s no matter how short the trace — **the trace length barely matters because the weight read dominates completely.** Batching 32 amortises that read across 32 sequences and lifts throughput 30×.

  Notice also that the slowdown ratio itself grows with batch: 1.1× at batch 1 (because KV is irrelevant when weights dominate) to 8.5× at batch 64 (because KV is now the dominant term). **These two effects are inseparable.** The batch size decides whether long traces are cheap, and the trace length decides how much of the batch's efficiency you keep.

  This is why a reasoning deployment is latency–throughput trade-off taken to its limit: it should run a very large batch, because a reasoning user is already waiting seconds and will tolerate the queueing.
</Callout>

## Context management: the actual toolkit

Three levers, and they compose.

**Cap the observation.** Truncate each tool result to a budget — say 2,000 tokens — before appending. This bounds the growth rate $o$. It is the cheapest fix and often the most effective, because most of a search result or file read is noise.

**Cache the prefix.** Non-negotiable. Everything above depends on it.

**Truncate the oldest turns.** When the context exceeds a budget, drop the oldest turns — or summarise them. This bounds $T$, the number of turns.

$$
\text{context} = \underbrace{s}_{\text{system}} + \underbrace{k \cdot o}_{\text{observations}} + \underbrace{g}_{\text{generated}}
$$

Cap $o$, bound $k$, keep $g$ as small as the task allows. That is three dials and a full solution.

<Callout type="real" title="Streaming the trace is a UX decision with a serving consequence">
  Whether the user sees 4,000 tokens of deliberation or only the final answer does not change the server's work at all — it is generated either way. But it changes the *perceived* latency enormously.

  Hiding it behind a "thinking" indicator and streaming only the answer makes the product feel 14 seconds faster while costing exactly the same. Worth knowing that this is free.

  The one caveat: if the trace is *not* appended to the context, you can cache a shorter prefix, which is a genuine server-side saving — but it only works for single-turn questions. Multi-turn reasoning conversations need the trace for coherence.
</Callout>

## Designing a knowledge agent

Everything so far treated the agent as one growing context. A real system has more moving parts, and each part decides how many LLM calls a task makes, how well the prefix cache works, and how long the slowest user waits. Take the most common kind: a **knowledge agent** that answers questions from a company's documents.

### The loop

It has five parts, and only two of them are the LLM:

1. **Planner.** An LLM call that reads the question and the list of tools and decides the next step: search for something, read a document, or answer.
2. **Tool registry.** The list of tools the agent may use, each with a name, a description, a JSON schema for its arguments (the format from "Structured output & tool calling") and who is allowed to call it. The registry's text is pasted into the planner's prompt, so **it is part of the prefix**.
3. **Executor.** Ordinary code, not an LLM. It checks the tool call against the schema and the caller's permissions, runs it with a timeout, and caps the size of the result before anything is appended.
4. **Retrieval.** The most important tool: a search over the document index that returns the best-matching chunks. This is the RAG pipeline from [RAG, CAG & the serving bill](/learn/prefill-prefix/rag-cag/), called by the agent instead of always running once before the model.
5. **Answer.** A final LLM call that writes the reply from the evidence gathered, with citations.

The loop is planner → executor → retrieval → planner, again and again, until the planner says "answer" or a step cap is reached. Two serving rules fall out at once. The <Term t="tool-registry">tool registry</Term> must be rendered **byte-identically** every time — tools in a fixed order, no timestamps — or the first pitfall above destroys the cache for every request. And choosing a different subset of tools for each request (with the router from [Semantic caching & semantic routing](/learn/routing-autoscaling/semantic-caching/), for example) makes the prompt shorter but gives each subset its own prefix, so the cache is shared among fewer requests. That is a trade worth measuring, not assuming.

### How much autonomy, and what it costs

"Agent" covers everything from a fixed script to a model that plans its own work. The <Term t="autonomy-level">level of autonomy</Term> — who decides the next step — is the biggest single decision for the serving layer:

| level | who decides the next step | LLM calls per task | prefix cache | tail latency |
|---|---|---|---|---|
| 0 · single call | nobody | 1 | system prompt shared by every request | one call |
| 1 · fixed workflow | your code, same steps every time | fixed, e.g. 6 | the same templates for every task, so high hit rates across requests; independent steps can run in parallel | fixed: the sum of the slowest path |
| 2 · routed workflow | the LLM picks a branch, your code runs it | fixed per branch | one shared prefix per branch | bounded by the longest branch |
| 3 · bounded loop | the LLM picks every step, up to a cap $K$ | 1 to $K + 1$ | perfect reuse inside a task, only the system prompt across tasks | the p99 task runs into the cap |
| 4 · fully autonomous | the LLM plans, replans, spawns sub-agents | no fixed number; only a budget stops it | each sub-agent starts a new prefix; summarising history invalidates the cache from the rewrite onward | set by the budget, not by the work |

Every step up the table buys flexibility and pays in three currencies.

**More calls.** A fixed workflow of 6 calls costs 6 calls. A bounded loop with $K = 8$ costs anywhere from 2 to 9, and the GPU must be sized for the mix, not the median.

**More cache churn.** A fixed workflow has the best caching of all: the same templates for every task mean thousands of requests share each prefix. A loop keeps perfect reuse *within* a task, but each task's context is its own. An autonomous agent that summarises its history to save space throws the cache away at that point: if it compresses 24,800 tokens of history into a 6,000-token summary and then appends a 3,000-token observation, the next call prefills 9,000 tokens instead of 3,000 — three times the work for that step.

**Worse tails.** This is the one people miss. Suppose each LLM call has a 1% chance of being slow (its own p99). A task finishes slowly if *any* of its calls is slow, so the chance a task of $n$ calls contains at least one slow call is

$$
1 - 0.99^{n}
$$

For one call that is 1%. For 6 calls it is 5.9%. For 20 calls it is **18.2%** — nearly one task in five hits a slow call. **An agent's p99 is not a call's p99**, and the more autonomous the agent, the larger $n$ gets and the less you control it. The levers are the ones from Module 24: tight per-call timeouts, a step cap, and a total time budget the executor enforces.

<Callout type="mentor" title="Use the least autonomy that does the job">
  Start at a fixed workflow. Move up a level only when you can name the questions the current level fails on. Most production knowledge agents are levels 1–3: the gain from full autonomy is real on open-ended research tasks, and its cost — unbounded calls, cold prefixes and long tails — lands on the serving layer whether or not the task needed it.
</Callout>

### Model selection: a router for steps

Not every step needs the big model. Planning and writing the final answer are hard: they need judgment. Reading one retrieved chunk and pulling out the relevant sentences is easy. <Term t="step-routing">Step routing</Term> applies the semantic-routing idea to each step of a task instead of each request: easy steps go to a small model, hard steps to a large one.

Here is a concrete task. The system prompt is cached on both fleets, so only the new tokens count:

| call | what it does | new input tokens | output tokens |
|---|---|---|---|
| 1 | plan | 100 (the question) | 150 |
| 2–5 | read one retrieved chunk each, write an extract | 1,600 each (question + 1,500-token chunk) | 100 each |
| 6 | answer from the extracts | 650 (question + plan + 4 extracts) | 400 |

Use illustrative prices for the cost of computing a token on each fleet: a **large** model at \$1.00 per million input tokens and \$3.00 per million output tokens, a **small** model at a tenth of that, \$0.10 and \$0.30.

**All large.** Input is 100 + 4 × 1,600 + 650 = 7,150 tokens. Output is 150 + 4 × 100 + 400 = 950 tokens.

$$
7{,}150 \times \frac{1.00}{10^6} + 950 \times \frac{3.00}{10^6} = 0.00715 + 0.00285 = 0.0100 \text{ dollars per task}
$$

**Routed: reads on the small model.** The large model still does calls 1 and 6: 750 input and 550 output tokens, \$0.00075 + \$0.00165 = \$0.0024. The small model does the four reads: 6,400 input and 400 output tokens, \$0.00064 + \$0.00012 = \$0.00076.

$$
0.0024 + 0.00076 = 0.00316 \text{ dollars per task}
$$

That is 0.0100 / 0.00316 = **3.2× cheaper**, a saving of 1 − 0.00316 / 0.0100 = **68%**. At a million tasks a day, \$10,000 becomes \$3,160.

Latency improves too. Give the large model a time to first token of 0.5 s and 30 ms per output token, and the small one 0.1 s and 10 ms. Running the steps one after another:

- **All large:** plan 0.5 + 150 × 0.03 = 5.0 s; each read 0.5 + 100 × 0.03 = 3.5 s, four of them 14.0 s; answer 0.5 + 400 × 0.03 = 12.5 s. Total **31.5 s**, and the first answer token appears at 5.0 + 14.0 + 0.5 = 19.5 s.
- **Routed:** plan 5.0 s; each read 0.1 + 100 × 0.01 = 1.1 s, four of them 4.4 s; answer 12.5 s. Total **21.9 s**, first answer token at 5.0 + 4.4 + 0.5 = 9.9 s — half the wait.

Two cautions keep this honest. First, a small model will sometimes write a bad extract, and a wrong extract becomes a wrong answer. The fix is the cascade from the semantic-routing lesson: when the answer step finds an extract unclear, it re-runs that read on the large model. A large read costs 1,600 × \$1.00/M + 100 × \$3.00/M = \$0.0019. If 20% of the 4 reads escalate, that is 0.8 extra large reads, \$0.00152, so the task costs \$0.00316 + \$0.00152 = \$0.00468 — still **2.1× cheaper** than all large.

Second, **route at call boundaries, not in the middle of one context.** The design above works because each reader starts its own short context. If one long agent context were handed from the small model to the large one, the large model's cache would hold none of it, and it would have to prefill the 6,000-plus tokens the small model had read — giving back most of the saving. Different models never share KV.

<Callout type="real" title="Parallel reads beat routing on latency">
  The four reads do not depend on each other, so a fixed workflow can run them at the same time. All large in parallel: 5.0 + 3.5 + 12.5 = 21.0 s. Routed in parallel: 5.0 + 1.1 + 12.5 = 18.6 s. Parallelism removes more latency than routing does, and only a workflow — not a free-running loop — knows in advance which steps are independent. Routing is the cost lever; structure is the latency lever.
</Callout>
