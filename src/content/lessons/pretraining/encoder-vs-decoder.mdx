Put yourself in early 2019 and place a bet. On one side, BERT: it has just swept eleven reading benchmarks, its ablation shows left-to-right models losing more than 10 points on question answering, and every research group is building on it. On the other side, GPT-2: impressive text, but its zero-shot task scores are often far below supervised systems.

Most people would have bet on the encoder. And for understanding benchmarks in 2019, they would have been right.

Yet every model you will serve in this course — Llama, Qwen, Mistral, and every chat assistant built on them — is a decoder. This lesson is about why the other horse won. None of the reasons is mysterious, and several of them are pure inference engineering.

## The three shapes

You have now met two ways to train the same transformer, and they differ by one thing: the attention mask, which decides which tokens each token may read. There is a third shape worth knowing, which combines them. The visual lays all three side by side, then puts numbers on the trade-offs.

<Scrolly>
  <ThreeMasks client:visible slot="stage" />

  <Step title="1. Encoder: everyone sees everyone">
    BERT's mask is full: every token attends to every other, so each token's vector is built from the **whole input**. Ideal for reading text you are given. But a model that sees everything cannot be graded on predicting the next token, so it plays the masked-word game, and it has no natural way to write.
  </Step>

  <Step title="2. Decoder: only the past">
    GPT's mask is causal: each token sees itself and earlier tokens, and the future is hatched out. It throws away half the matrix and in exchange gets two things: **every position can be graded** and **new text can be written**, one token at a time.
  </Step>

  <Step title="3. Encoder–decoder: read, then write">
    The original 2017 Transformer and T5 use two stacks. The **encoder** reads the input with full attention. The **decoder** writes the output causally and, through **cross-attention**, every output token reads the whole encoded input. Only output tokens are graded.
  </Step>

  <Step title="4. Every token teaches, or 15% do">
    Same forward pass, same compute. The causal objective grades **every position**; the masked objective grades about **15%**. Drag the length: the ratio is always 1 / 0.15 ≈ 6.7. Each masked prediction is richer, but there are far fewer of them.
  </Step>

  <Step title="5. Append one token: what changes?">
    Add a token to a decoder: one new row appears and every old row is exactly as it was, because old rows cannot see the new token. **Their keys and values can be cached.** Add a token to an encoder: every old row can see it, so every row in every layer changes.
  </Step>

  <Step title="6. The cost of writing">
    Generating with a decoder and a KV cache costs about one token-forward per new token. An encoder made to write would have to re-read the whole sequence after every token. After a 500-token prompt, 500 new tokens cost **1,000** token-forwards against **375,250**.
  </Step>

  <Step title="7. One interface: text in, text out">
    A decoder continues text, and almost any task can be written as text to continue: classify, extract, translate, code, chat. **One objective, one model, one serving stack.** Requests for different tasks can even share a batch on the same GPU.
  </Step>

  <Step title="8. Where encoders still win">
    When the job is reading with no writing — **search embeddings, rerankers, classifiers** — a small encoder sees both sides, runs in one pass and costs a fraction of a large decoder. These are workhorses of Module B3.
  </Step>
</Scrolly>

## Then derive it properly

### Reason 1: every token teaches

Recall the counts from lessons 1 and 3. On a sequence of $T$ tokens:

$$
\text{causal: } T \ \text{graded predictions}, \qquad \text{masked: } 0.15\,T \ \text{graded predictions}
$$

For $T = 512$ that is 512 against 76.8: a ratio of ${}1 / 0.15 = 6.67$. Both cost essentially the same forward and backward pass, because the expensive part — pushing every token through every layer — happens either way. The masked model simply throws away the gradient signal at 85% of the positions it paid to compute.

This is not the whole story, and it is worth being fair. A masked prediction sees both sides of the gap, so each one is a richer question, and the BERT paper reports that its masked model converged only slightly slower than a left-to-right one while ending up far better at reading tasks. Later encoder research took the waste seriously: ELECTRA (2020) replaced "predict the masked token" with "spot which tokens were swapped", precisely so that *every* position gives a training signal. But the basic arithmetic favours the decoder, and at the scale of trillions of tokens a factor of six in supervision per pass is not a detail.

### Reason 2: one objective covers every task

An encoder produces vectors. To turn vectors into an answer you need a head, and a head is specific to one task: two classes for sentiment, a start and end vector for question answering, one tag per token for entities. Every new task means a new head, new labelled data and a new copy of the model (lesson 3).

A decoder produces *text*. And as lesson 4 showed, nearly any task can be phrased as text to continue:

| Task | Prompt | Continuation |
|---|---|---|
| classify | Review: "Battery died in an hour." Sentiment: | negative |
| extract | Email: "…meet at 3 pm Friday…" Meeting time: | 3 pm Friday |
| translate | English: see you tomorrow. French: | à demain |
| chat | User: why is the sky blue? Assistant: | Sunlight scatters… |

The training objective and the user interface are the same thing. That is why the improvements GPT-2 showed with scale carried straight over into general-purpose assistants (Module 3C), with no new head anywhere.

<Callout type="real" title="Why this matters on the serving side">
  With one encoder per task, a product that needs sentiment, extraction and translation runs three different models, each with its own GPUs, memory and deployment. With one decoder, all three are just different prompts: requests for every task arrive at the same engine and can be batched together in the same forward pass. Continuous batching (Module 07) and prefix caching (Module 10) both assume exactly this world of one model serving everything.
</Callout>

### Reason 3: decoders can write, and writing can be cached

Generation means adding one token at a time and reading the result back in. Ask what each architecture has to recompute when the sequence grows from $t$ to $t + 1$ tokens.

**Decoder.** Row $i$ of the attention matrix only reads columns $\le i$. The new token sits in column $t + 1$, which no earlier row may read. So every earlier token's hidden state, in every layer, is exactly what it was before, and so are its keys and values. Only the new token needs computing; its attention reads the stored keys and values of everything before it. Storing them is the <Term t="kv-cache">KV cache</Term>, and Module 05 builds it.

**Encoder.** Every row reads every column, including the new one. Add a token and every earlier token's representation changes in the very first layer, which changes the input to the second layer, and so on all the way up. Nothing can be reused. Each new token means re-reading the whole sequence.

<Callout type="math" title="Worked: 500 new tokens after a 500-token prompt">
  Count the work in *token-forwards*: one token pushed through the whole model once.

  **Decoder with a KV cache:** the prompt is processed once (500 token-forwards), then each new token costs one: ${}500 + 500 = 1{,}000$.

  **Encoder, re-reading everything:** generating the $i$-th new token means a full pass over ${}500 + i$ tokens:

  $$
  \sum_{i=1}^{500} (500 + i) = 500 \times 500 + \frac{500 \times 501}{2} = 250{,}000 + 125{,}250 = 375{,}250
  $$

  **375 times more work.** In general, $n$ new tokens after $P$ prompt tokens cost $P + n$ for the decoder and $nP + n(n+1)/2$ for the encoder. The decoder is linear in $n$; the encoder is quadratic.
</Callout>

That quadratic is the reason "BERT for text generation" never became a thing, and the linear line is the reason the whole of Parts 2 to 8 of this course exist: once generation costs one token-forward per token, the game becomes making that one step as cheap as possible.

<Callout type="pitfall" title="A decoder still reads the prompt both ways… almost">
  It is tempting to think a decoder "only understands left context". But by the time the model reaches the *last* prompt token, that token has attended to every earlier token, so its vector does summarise the whole prompt. What a decoder lacks is that *early* tokens never see *later* ones. In practice, for generation that hardly matters: the next token is predicted from the last position, which sees everything. It matters more for embeddings, which is one reason encoders hold on there.
</Callout>

### Reason 4: simplicity that scales

The last reason is less a theorem than an engineering fact. A decoder-only model is **one stack, one mask, one objective, one cache**. The prompt and the output live in one sequence, so a multi-turn conversation is just a longer sequence, with no question of where the "input" ends and the "output" begins. Training code, inference engines, quantisation tools, kernels and parallelism schemes all target that one shape. And lesson 4 showed it keeps getting better with size; Module 3B shows how predictably. Once the field found a design that improved smoothly with scale and served every task through one interface, the incentive to make anything else larger mostly disappeared.

## The middle road: encoder–decoder

There is a third design, and it is not a loser. An <Term t="encoder-decoder">encoder–decoder</Term> keeps both stacks: an encoder reads the input with full attention, and a decoder generates the output causally while also attending to every encoder output through <Term t="cross-attention">cross-attention</Term>. In cross-attention the queries come from the decoder and the keys and values come from the encoder, so each output token can consult the whole input at every layer.

This was the shape of the original 2017 Transformer, built for translation, where it is natural: read the whole French sentence, then write the English one. Its best-known descendant is **T5** (Raffel et al., 2019), which framed *every* task as text-to-text — "translate English to German: …", "summarize: …" — and pretrained with a masked objective that hides whole spans of tokens. In T5's own careful comparison at the sizes it tested, the encoder–decoder actually came out slightly ahead of a decoder-only model. Encoder–decoders are still used where the input and output are clearly separate, such as speech recognition (OpenAI's Whisper is one).

So why did general-purpose LLMs not go this way? Mostly the reasons above. Two stacks and two kinds of attention are more machinery to scale and serve. Only the output tokens are graded during training. And in a chat, where every answer becomes part of the next prompt, the clean split between "input" and "output" that an encoder–decoder relies on stops existing.

| | Encoder | Decoder | Encoder–decoder |
|---|---|---|---|
| Attention | full | causal | full (input) + causal and cross (output) |
| Typical objective | masked tokens | next token | masked spans in, text out |
| Graded per pass | ~15% of tokens | every token | output tokens |
| Can generate | no | yes | yes |
| KV cache for generation | not possible | yes | yes (decoder side) |
| Examples | BERT, RoBERTa, embedding models | GPT-2, Llama, Qwen, Mistral | original Transformer, T5, Whisper |

## Where encoders still win

Do not take "decoders won" to mean encoders are obsolete. For jobs that only read, they are often the best tool, and they run all over production systems:

- **Search embeddings.** Turn each document and each query into one vector and compare them with a dot product (*Dot products & softmax*, Module 01). You embed millions of documents once and each query once, so the embedding model's cost and quality per token matter enormously, and seeing both sides of every word helps. Module B3 builds this.
- **Rerankers.** Read a query and a candidate document *together*, in one input, and output a relevance score. Full attention between the two is exactly what an encoder does best. Also Module B3.
- **Classifiers.** Spam, toxicity, language identification, routing a request to the right model, the guardrails of Module B7. A label is all you need, so there is nothing to generate.

The cost argument is stark. To classify a 200-token message:

$$
\text{BERT-Base: } 2 \times 110\text{M} \times 200 \approx 44\ \text{GFLOP}, \qquad \text{an 8B decoder: } 2 \times 8\text{B} \times 200 = 3.2\ \text{TFLOP}
$$

The decoder spends about ${}8{,}000 / 110 \approx 73$ times more compute just to read the input, before it generates a single token of its answer. At millions of requests a day that is the difference between one modest GPU and a fleet. Encoder development has not stopped either: at the time of writing, newer encoders such as ModernBERT (2024) bring decoder-era improvements — longer context, better attention kernels — back to the encoder.

<Callout type="intuition" title="Two jobs, still">
  The module's title is literal. One transformer, two training games, two jobs. **Fill in the blank** produces a reader: cheap, bidirectional, excellent at turning text into vectors and labels. **Finish the sentence** produces a writer: it can do any task you can phrase as text, it learns from every token, and its generation can be cached. The writer won the race to become the general-purpose model. The reader kept the jobs that never needed writing.
</Callout>

<KeyNotes>
  1. Encoder, decoder and encoder–decoder are the same transformer with different attention masks: full, causal, or full input plus causal output with cross-attention.
  2. Per pass, a causal objective grades all $T$ positions and a masked one about ${}0.15\,T$: roughly 6.7× more supervision for the same compute.
  3. A decoder phrases every task as text to continue, so one objective and one model serve every task, and different tasks can share one batch.
  4. In a decoder, earlier tokens never see later ones, so their keys and values never change and can be cached. In an encoder, every new token changes every token in every layer.
  5. Generating $n$ tokens after a $P$-token prompt costs about $P + n$ token-forwards for a cached decoder and $nP + n(n+1)/2$ for a re-reading encoder: 1,000 against 375,250 for $P = n = 500$.
  6. Decoder-only is one stack, one mask, one cache and one sequence, and it improves smoothly with scale, which is why the whole tool chain converged on it.
  7. Encoder–decoders (original Transformer, T5, Whisper) suit tasks with a clear input and output; in chat, that split disappears.
  8. Encoders still win for search embeddings, rerankers and classifiers: reading only, both sides, one pass, about 73× less compute than an 8B decoder on the same input.
</KeyNotes>
