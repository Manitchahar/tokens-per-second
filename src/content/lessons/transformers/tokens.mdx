Type a prompt into a chatbot and something happens before the GPU ever sees it: the text is chopped into **tokens**, and each token is replaced by an integer. "Hello world" might arrive as `[15339, 1917]`. Everything downstream — the embedding lookup, the attention matrix, the <Term t="kv-cache">KV cache</Term>, your bill — is counted in those integers. Get the count wrong and every number in the rest of this course is wrong.

An inference engineer needs three things from tokenizers: how to read one, how to count with one, and what a bad one costs.

## Why not just feed characters?

The earliest language models did use characters, and it works — but character by character, "unbelievable" is 12 items and "tokenization" is 12. Every item costs a full pass through a 4,096-wide hidden state, an attention row, and a slot in the KV cache. You would be spending your whole memory budget on spelling.

Words would be better, but English has hundreds of thousands of them, plus every language, every proper noun, every number, every typo. The vocabulary would be enormous and most entries would be used once.

The answer most people landed on: **learn the most common pieces of text from a huge corpus, and add a guaranteed fallback so nothing is ever impossible.**

## Byte-pair encoding, from scratch

**Byte-pair encoding (BPE)** works in four steps.

**1. Start with characters.** Every character becomes its own token. Your 28-character sentence `the transformer reads tokens` is 28 tokens. Useless, but total.

**2. Count adjacent pairs.** In English text the pair `t`+`h` occurs constantly. So do `he`, `in`, `er`, ` th`.

**3. Merge the most frequent pair.** Replace every occurrence of that pair with a new single token. `t`+`h` becomes `th`, a new token with a new ID. Recount.

**4. Repeat until you hit your budget.** Each merge shortens the text a little: one token disappears for every place the pair occurred. And each merge adds exactly one entry to the vocabulary, so the budget is simply a number of merges. GPT-2 (2019) stopped after 50,000: 256 byte tokens + 50,000 merges + 1 end-of-text marker = **50,257** entries. LLaMA-1 and Llama-2 use **32,000**; Llama-3.1 uses 128,000 learned tokens plus 256 reserved special tokens, **128,256**.

The result, in the visual, for our toy sentence:

| | pieces | chars per token |
|---|---|---|
| Characters only | 28 | 1.00 |
| After a few merges | `the` · ` ` · `trans` · `form` · `er` · ` ` · `read` · `s` · ` ` · `tok` · `ens` = 11 | 2.55 |
| After all merges | `the` · ` ` · `transformer` · ` ` · `reads` · ` ` · `tokens` = 7 | **4.00** |

<Callout type="math" title="Characters per token is the number to memorise">
  English prose runs at roughly **4 characters per token**, or about **1.3 tokens per word**. Keep the reciprocal too: **1 token ≈ 0.75 English words**, so 1,000 tokens is about 750 words. Every "tokens per second" figure, every context-length claim and every price depends on this ratio.
</Callout>

## Each piece is just an integer

A tokenizer is two dictionaries and a merge list:

- **encode(text) → list of IDs**: greedily apply merges, then look each piece up in the vocabulary
- **decode(ids) → text**: look each ID up, concatenate the pieces
- **the vocabulary**: a list mapping piece → ID, in a fixed order

That ID is the *only* representation of your text inside the model. `15339` does not mean "Hello" in any way the model can inspect — it is an index, and the meaning arrives one step later when that index selects a row of a table.

    The base of a byte-level vocabulary is **all 256 byte values**, one token each. Anything on earth can therefore be spelled out, so the tokenizer never needs an "unknown" symbol.   </Step>

  <Step title="6. A token is not free">
    Every token costs an embedding row (8 KB read), a row in every attention score matrix, and a KV cache entry in every layer that stays alive for the whole request. That is why a tokenizer that emits 10% more tokens makes a prompt measurably slower and more expensive.
  </Step>
</Scrolly>

## The real vocabularies

| Model | Vocabulary | Made of | Character ratio | Special tokens |
|---|---|---|---|---|
| GPT-2 | 50,257 | 256 bytes + 50,000 merges + 1 special | ≈ 4.0 | `<\|endoftext\|>` |
| Llama-2 | 32,000 | SentencePiece BPE, incl. 256 byte-fallback pieces | ≈ 3.2 | `<unk>`, `<s>`, `</s>` |
| Llama-3.1 | 128,256 | 128,000 byte-level BPE + 256 reserved special | ≈ 4.0 | 256 reserved, e.g. `<\|begin_of_text\|>` |
| Qwen2.5 | 151,936 | 151,643 byte-level BPE + special tokens, padded | ≈ 3.6 | `<\|im_start\|>`, `<\|im_end\|>`, … |
| GPT-4 | ~100,000 | byte-level BPE | ≈ 4.0 | |

Three things worth noticing. **Byte-level BPE with a 256-byte floor came from GPT-2** (2019): with every byte available as a token there is nothing left to be unknown, so there is no `<unk>`. LLaMA-1 and Llama-2 took a different route, a SentencePiece tokenizer that falls back to 256 byte pieces for rare characters but still keeps an `<unk>` entry; Llama-3 switched to GPT-2-style byte-level BPE and inherits the floor. Second, **special tokens** such as `<|im_start|>` are entries the chat template injects to mark conversation roles. They are real tokens that consume real context. Third, **the sizes are often padded**: Qwen2.5's tokenizer has 151,643 learned tokens plus a couple of dozen special ones, but its embedding table has 151,936 rows, rounded up so the matrix shapes suit GPU kernels. Karpathy's nanoGPT does the same to GPT-2, padding 50,257 to 50,304 (a multiple of 64) purely for speed. Unused rows are never produced by the tokenizer.

<Callout type="pitfall" title="Non-English text and code are much denser">
  The 4-characters-per-token figure is *English prose*. Two cases that will bite you:

  - **Code and numbers.** `tokenizer.encode("def f(x): return x**2")` produces far more tokens per character than prose, because source code is full of rare short pieces and no natural word structure. Assume 2.5–3 characters per token.
  - **CJK and other non-Latin scripts.** Chinese, Japanese and Korean usually cost around **one token per character or more**, because a single Han character carries more meaning than an English letter but the vocabulary needs one entry per common character. A prompt in Chinese can be 2–3× more tokens than the same meaning in English.

  If your product is multilingual, the tokenizer's vocabulary is not a detail — it is a per-language pricing decision.
</Callout>

## Tokens in a real request

You will never send bare text to an instruct model. The **chat template** wraps your messages in special tokens that mark who is speaking and where turns begin and end. Qwen2.5's template, for a two-turn conversation, looks like this — and every marker is a token:

```
<|im_start|>system
You are a helpful assistant.<|im_end|>
<|im_start|>user
Explain the KV cache.<|im_end|>
<|im_start|>assistant
```

Count those markers and you will see the overhead that surprises people: **a three-message conversation with 12 words of actual content is about 40 tokens.** Roughly 8–10 tokens of pure framing, plus 3–4 per additional message. If you are budgeting a context window for an agent that makes twenty tool calls in a row, the framing is a real line item — 20 × 10 = 200 tokens of nothing but scaffolding.

Three practical consequences:

- **The number an API reports is the number that matters.** `usage.prompt_tokens` from the provider counts the *templated* string, markers included. Your own client-side estimate will be slightly low if you forget the template.
- **Prefixes are made of tokens too**, which is what makes prefix caching (Module 10) work: if many requests share a system prompt, that shared prefix is a contiguous span of tokens that can be reused rather than recomputed.
- **Never concatenate two token IDs and expect one token back.** Encoding is not additive across a boundary; `"token" + "ization"` is two pieces that *might* merge into one, and only if the merge exists in the vocabulary.

<Callout type="math" title="The budget you are actually managing">
  For a request with a 2,000-token system prompt, a 3,000-token user message and a 500-token answer:

  | | tokens | KV cache (Llama-3.1-8B) |
  |---|---|---|
  | Template markers | ~25 | 3 MiB |
  | System prompt | 2,000 | 250 MiB |
  | User message | 3,000 | 375 MiB |
  | Answer being generated | 500 | 62 MiB |
  | **Total at the end** | **5,525** | **691 MiB** |

  The markers are 0.5% of the tokens and 0.4% of the memory. Nobody optimises them. Nobody should.
</Callout>

## Tokens are the unit of everything

Once you can count tokens, every other number in this course becomes computable. For Llama-3.1-8B, which Module 02's cheat sheet derived:

$$
\text{KV cache bytes} = T \times 2 \times 32 \times 8 \times 128 \times 2 = T \times 131{,}072 \text{ bytes}
$$

so a 4,000-token prompt holds 4,000 × 131,072 = **500 MiB** of KV cache. And 4,000 tokens of English prose is about 16,000 characters: roughly four paragraphs.

| Prompt | Characters | Tokens | KV cache (Llama-3.1-8B) |
|---|---|---|---|
| A one-line question | 60 | 15 | 1.9 MiB |
| A code review request | 2,400 | 960 | 120 MiB |
| A long document | 16,000 | 4,000 | 500 MiB |
| The same document in Chinese | 4,000 chars | ~5,500 | 688 MiB |

**The multiply you will do in production.** $T = 8{,}192$ tokens × 131,072 bytes = **1.07 GB** of KV cache for one user. On an 80 GB H100 with 16.1 GB of Llama-3.1-8B weights, that is 1.07 GB per concurrent sequence — about 58 sequences before the card is full. Module 05 is entirely about that arithmetic, and it is the arithmetic that decides how many users one GPU can serve.

## In code

Everything a tokenizer is, in twenty lines:

```python
import regex as re                      # the split pattern is part of the tokenizer

class TinyBPE:
    def __init__(self, merges):          # merges: [("t","h"), ("th","e"), ...] in learned order
        self.ranks = {p: i for i, p in enumerate(merges)}
        self.vocab = {bytes([b]): b for b in range(256)}   # 256 byte tokens: the floor

    def encode(self, text: str) -> list[int]:
        # 1. bytes: every character is 1-4 bytes, every byte has an ID
        parts = [bytes([b]) for b in text.encode("utf-8")]
        while True:
            # 2. find the adjacent pair with the best (lowest) merge rank
            best, at = None, -1
            for i in range(len(parts) - 1):
                r = self.ranks.get((parts[i], parts[i + 1]))
                if r is not None and (best is None or r < best):
                    best, at = r, i
            if at < 0: break
            # 3. merge that one pair everywhere
            parts[at:at + 2] = [parts[at] + parts[at + 1]]
        return [self.vocab.setdefault(p, len(self.vocab)) for p in parts]

tok = TinyBPE([(b"t", b"h"), (b"th", b"e"), (b"r", b"e"), (b"a", b"d"), (b" ", b"t")])
ids = tok.encode("the transformer reads tokens")
print(ids, len(ids))                     # 7-ish ids for a 28-character sentence
print(b"".join(tok.vocab[i] for i in ids))  # -> b'the transformer reads tokens'
```

Real tokenizers add one thing: they never let a merge cross a category boundary. GPT-style tokenizers split on a regex first — words, numbers and punctuation each merge separately, and the leading space of a word is part of the piece (`Ġthe`, `Ġtok`) rather than a separate token. Llama-3's `Ġ` is just a visible marker standing in for a real space byte.

<Callout type="real" title="What this means when you serve a model">
  The tokenizer is part of the model. It ships with the weights, its vocabulary size is baked into the embedding matrix, and a server must run it on every request — in the request path, before the GPU. It also means your context window is a *token* budget, so a "128K context" model accepts fewer characters of code than of prose. At the time of writing, most production engines run the tokenizer in Rust on the CPU, batched with continuous batching, because it is pure overhead you cannot avoid.
</Callout>

<KeyNotes>
  1. A model reads **integers, not text**. A token is a piece of text plus an integer ID, and the ID is a row number, not a meaning.
  2. **Byte-pair encoding** starts from bytes, repeatedly merges the most frequent adjacent pair, and stops at a fixed vocabulary size. Every merge is one learned rule.
  3. English runs at about **4 characters per token**, about **1.3 tokens per word** (1 token ≈ 0.75 words). Code is denser (≈ 2.5–3 characters per token); CJK is much denser still (≈ 1 token per character).
  4. A byte-level vocabulary starts with **all 256 byte values**, one token each, so no input is ever unknown and no `<unk>` token is needed. GPT-2 introduced this in 2019; Llama-3 and Qwen2.5 inherit it.
  5. Vocabulary sizes: GPT-2 50,257 (256 bytes + 50,000 merges + 1 special) · Llama-2 32,000 · Llama-3.1 128,256 (128,000 learned + 256 reserved special) · Qwen2.5 151,936 (151,643 learned + special tokens, padded).
  6. **Tokens are the billing unit.** Everything else — KV cache, context limit, prefill cost, tokens per second — is denominated in tokens.
  7. KV cache for Llama-3.1-8B = $T \times 131{,}072$ bytes. 8,192 tokens = **1.07 GB** for a single sequence.
  8. Word-start spaces are part of the token (`Ġthe`), and merges never cross a word/number/punctuation boundary.
</KeyNotes>
