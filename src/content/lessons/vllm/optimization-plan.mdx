In [Metrics & tuning one GPU](/learn/vllm/tune-one-gpu/), you learned how vLLM divides memory between model weights, a runtime reserve, and the KV cache pool, and how capping batch size limits per-step latency.

Yet when teams optimize real deployments, panic often replaces arithmetic. An engineer facing high latency changes four flags at once, runs an ad-hoc benchmark, sees raw throughput tick up 15%, and ships to production. Under real peak traffic, tail latency explodes, streams freeze, and the server runs out of memory. Changing four knobs at once taught them nothing about what broke.

Inference engineering is an empirical science. Production optimization demands an <Term t="optimization-plan">optimization plan</Term>: seven deliberate stations that isolate variables and test hypotheses systematically. In this lesson, we derive the theoretical boundaries for serving **Qwen3-14B in BF16 on one NVIDIA L40S 48 GB** (an AWS `g6e.2xlarge`), check them against the numbers a real run of vLLM printed, establish a measured baseline, and judge every change under a strict keep-or-revert rule.

## The seven-station optimization method

Optimization is an iterative cycle. Before touching a single flag, understand your hardware, lock your workload, and define acceptable performance.

<Scrolly>
  <OptimizationPlan client:visible slot="stage" />

  <Step title="1. Examine the hardware">
    Everything begins with the physical hardware. Run `nvidia-smi` to verify GPU architecture, HBM capacity, memory bandwidth, and interconnect topology. The laws of physics dictate your serving ceiling before you execute any code.
  </Step>

  <Step title="2. Define the workload">
    You cannot optimize against a moving target. Fix the workload using a reproducible <Term t="traffic-generator">traffic generator</Term>. Lock down prompt and output length distributions, target request arrival rates, and request burstiness.
  </Step>

  <Step title="3. Define metrics and an SLO">
    Raw throughput without latency constraints is a vanity metric.   </Step>

  <Step title="4. Deploy the default baseline server">
    Launch the serving engine with clean default configuration parameters. Inspect the startup banner to log the exact memory allocations: model weights, system reserve, and the initialized KV cache pool.
  </Step>

  <Step title="5. Benchmark the baseline">
    Send your reproducible test workload against the baseline server. Collect TTFT, inter-token latency, throughput and, if your harness computes it against the SLO, <Term t="goodput">goodput</Term>. This creates row zero of your optimization ledger.
  </Step>

  <Step title="6. Change ONE knob">
    Formulate a concrete hypothesis and modify exactly one configuration variable (for instance, swapping in a 4-bit checkpoint, reducing `max_model_len` or bounding `max_num_seqs`). Never change two variables in the same experiment.
  </Step>

  <Step title="7. Record and decide (keep or revert)">
    Re-benchmark under identical traffic and log the outcome. Apply the <Term t="keep-or-revert">keep-or-revert rule</Term>: if goodput improves while all SLO boundaries hold, keep the change; if latency violates your SLO or tail jitter spikes, revert immediately.
  </Step>

## Station 1 · Examine the hardware

Before touching configuration files, audit the host machine with `nvidia-smi`:

```bash
nvidia-smi --query-gpu=name,compute_cap,memory.total,memory.free \
  --format=csv,noheader
```

On an idle `g6e.2xlarge` this prints the GPU name, compute capability **8.9** (Ada Lovelace) and **46,068 MiB** of memory, which is 45.0 GiB: the card's 48 GB minus what ECC and the driver keep for themselves.

Four hardware parameters govern your serving ceiling:

1. **Total GPU memory:** 48 GB of GDDR6, of which vLLM sees 45.0 GiB. Every gigabyte allocated to weights or runtime scratch is a gigabyte taken away from the KV cache pool.
2. **Memory bandwidth:** about **864 GB/s** (NVIDIA spec sheet). As proven in [The two speed limits](/learn/gpu-first-principles/two-speed-limits/), autoregressive decode is memory-bandwidth bound, so this number sets the decode speed.
3. **Compute throughput:** about **362 TFLOP/s** of dense BF16 tensor-core math (733 TFLOP/s in FP8, which Ada supports). Prefill is compute-bound and uses this.
4. **Interconnect topology:** the L40S has **no NVLink**. GPUs talk over PCIe Gen4 x16, about 32 GB/s each way. On a one-GPU instance that does not matter; split a model across two L40S cards and every all-reduce crosses PCIe (Module 18).

<Callout type="mentor" title="Audit the machine before trusting the numbers">
  Running `nvidia-smi` confirms no background processes occupy GPU memory, verifies that clocks run at performance state P0 rather than idle state P8, and ensures CUDA drivers match your serving engine container.
</Callout>

## Station 2 · Define the workload

A benchmark is meaningless unless the traffic pattern is fixed and reproducible. As taught in [Workloads, warm-up & reproducible runs](/learn/benchmarking/workloads-reproducibility/), optimizing against variable traffic only measures noise.

Production workloads fall into distinct categories:

- **Conversational chat (ShareGPT):** Balanced prompts (100–500 tokens) and completions (150–400 tokens).
- **Document summarization / RAG:** Large prompt contexts (2,000–32,000 tokens) and concise completions (100–300 tokens), heavily prefill-bound.
- **Code generation / Reasoning:** Short prompts (50–200 tokens) and extensive completions (1,000–4,000 tokens), spending over 90% of execution time in decode.

Benchmark using standard datasets like ShareGPT and dispatch traffic with a client-server harness under controlled arrival rates, rather than unrealistic sequential client loops.

<Callout type="real" title="The workload can move the number more than any flag">
  On the same L40S server, with the same flags, `vllm bench serve` with its **prefix-repetition** dataset (many prompts sharing long prefixes) measured **1,123 tok/s** of total throughput, against 474 tok/s for ShareGPT below. Nothing in the engine changed: repeated prefixes hit vLLM's prefix cache, which is on by default, so most prompt tokens were never recomputed (Module 10). A tuning result is only meaningful next to the workload that produced it.
</Callout>

## Station 3 · Define metrics and an SLO

In [SLOs & goodput](/learn/benchmarking/slos-goodput/), we established that raw throughput alone is dangerous. A server producing 2,000 tokens per second is worthless if users wait 12 seconds for the first token.

Define your Service Level Objective (<Term t="slo">SLO</Term>) across four core metrics:

1. **TTFT (Time to First Token):** Time from request dispatch until the first token streams back (queueing plus prefill). Target for this lab: mean TTFT &lt; 200 ms.
2. **ITL (inter-token latency):** The gap between consecutive streamed tokens; its average is TPOT. Comfortable reading needs roughly 20 tokens/s or better, so 50 ms per token or less. Target for this lab: p99 ITL &lt; 100 ms, so even the worst gaps stay invisible.
3. **Total throughput:** Aggregate tokens (prompt plus output) processed per second across all concurrent users.
4. **Goodput:** Output tokens per second delivered strictly within your TTFT and ITL SLO thresholds.

## First principles: Qwen3-14B on one L40S

Let us calculate the physical performance limits for **Qwen3-14B** in BF16 on an **NVIDIA L40S 48 GB**, using public architecture specifications at the time of writing, and then compare each one with what vLLM printed when it started.

### 1. Model weight memory footprint

Qwen3-14B contains about 14.8 billion parameters. In 16-bit brain floating point (`bfloat16`, 2 bytes per weight):

$$
\text{Weights} \approx 14.8 \times 10^9 \times 2\ \text{bytes} \approx 29.5\ \text{GB} = 27.5\ \text{GiB}
$$

vLLM reports memory in GiB (${}2^{30}$ bytes), and its log says the model took **27.5 GiB**. From here on this lab uses GiB, because that is what the logs print.

### 2. KV cache per token

From Qwen3-14B's public configuration:
- Transformer layers: $L = 40$
- Key/Value attention heads: $n_{kv} = 8$ (Grouped-Query Attention)
- Head dimension: $d_{head} = 128$
- Data type: 2 bytes per element (`bfloat16`)

Using the formula from [Blocks, block tables & PagedAttention](/learn/paged-attention/blocks-and-tables/):

$$
\text{KV bytes per token} = 2 \times L \times n_{kv} \times d_{head} \times \text{bytes}
$$

$$
\text{KV bytes per token} = 2 \times 40 \times 8 \times 128 \times 2 = 163{,}840\ \text{bytes} = 160\ \text{KiB}
$$

Every token retained in the engine's memory pool requires 160 KiB of GPU memory.

### 3. KV cache pool budget at 90% utilization

Deploying with `--gpu-memory-utilization 0.90` sets the budget against the memory vLLM can see:

$$
\text{Budget} = 0.90 \times 45.0\ \text{GiB} = 40.5\ \text{GiB}
$$

Subtract the weights (27.5 GiB). At startup vLLM also profiles a forward pass to measure peak activations, CUDA-graph buffers and other non-weight allocations; here they come to about 2.0 GiB. What remains is the KV cache pool:

$$
\text{KV cache pool} = 40.5 - 27.5 - 2.0 \approx 11.0\ \text{GiB}
$$

In terms of token capacity:

$$
\text{Pool capacity} = \frac{11.0 \times 2^{30}\ \text{bytes}}{163{,}840\ \text{bytes/token}} \approx 72{,}089\ \text{tokens}
$$

vLLM's log says **72,064 tokens**: the same figure, cut down to whole 16-token blocks (4,504 of them) from the unrounded pool size.

### 4. Maximum concurrency at the default context

Qwen3-14B's config advertises a 40,960-token context, and vLLM defaults `--max-model-len` to that. In the worst case, where every active request reaches the ceiling:

$$
\text{Worst-case KV per request} = 40{,}960 \times 163{,}840\ \text{bytes} = 6.25\ \text{GiB}
$$

$$
\text{Max concurrency} = \frac{72{,}064}{40{,}960} \approx 1.76
$$

vLLM prints exactly this: **"Maximum concurrency for 40,960 tokens per request: 1.76x"**. Fewer than two worst-case requests fit. Real ShareGPT requests are a few hundred tokens long, so far more run in practice, but 1.76× is what the engine can *promise*. Capping `--max-model-len` at 8,192 would raise it to ${}72{,}064 / 8{,}192 = 8.8\times$.

### 5. Single-stream decode speed ceiling

During single-user decode ($B = 1$), the GPU must stream all 29.5 GB of weights for every output token. At 864 GB/s the absolute physical ceiling is

$$
\text{Decode ceiling} = \frac{864\ \text{GB/s}}{29.5\ \text{GB}} \approx 29.3\ \text{tokens/s}, \qquad t_{\text{step}} \ge 34.2\ \text{ms}
$$

No software can beat that for unquantized single-stream Qwen3-14B on this card. With about 80% of peak bandwidth achieved (${}691$ GB/s) and ~1.5 ms of launch and scheduling overhead:

$$
t_{\text{step}} \approx \frac{29.5\ \text{GB}}{691\ \text{GB/s}} + 1.5\ \text{ms} \approx 42.7 + 1.5 = 44.2\ \text{ms} \;\Rightarrow\; \approx 22.6\ \text{tokens/s}
$$

<Callout type="math" title="First-principles calculations prevent bad benchmarks">
  Knowing your ceiling (29 tok/s upper bound, about 23 tok/s practical per stream) prevents bad benchmarking. If a single-stream run reports 60 tok/s for BF16 Qwen3-14B on an L40S, your harness is measuring cached prefixes or timing incorrectly. And the ceiling predicts the benchmark below before you run it: a decode step costs about 43 ms whether it serves one stream or ten.
</Callout>

## Station 4 · Deploy the baseline server

Launch the baseline server with defaults (no `--max-model-len`, so it is 40,960):

```bash
vllm serve Qwen/Qwen3-14B \
  --dtype bfloat16 \
  --gpu-memory-utilization 0.90 \
  --port 8000
```

Notice that every continued line ends with a trailing backslash `\`.

Verify readiness with standard endpoints before generating load:

```bash
# Check model registration
curl http://localhost:8000/v1/models

# Send warm-up request
curl http://localhost:8000/v1/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "Qwen/Qwen3-14B", "prompt": "Hello", "max_tokens": 5}'
```

The startup log confirms the arithmetic. The four lines that matter on this machine (format at the time of writing, other lines omitted):

```
Model loading took 27.5 GiB
Available KV cache memory: 11.00 GiB
GPU KV cache size: 72,064 tokens
Maximum concurrency for 40,960 tokens per request: 1.76x
```

Every one of those numbers was predictable from the config file and `nvidia-smi`. If they had not matched, that mismatch would have been the first thing to investigate.

## Station 5 · Benchmark the baseline

Drive the server using vLLM's native benchmark utility: `vllm bench serve`. Avoid custom Python timing loops, which distort inter-token streaming measurements.

```bash
vllm bench serve \
  --backend vllm \
  --base-url "http://localhost:8000" \
  --model Qwen/Qwen3-14B \
  --dataset-name sharegpt \
  --dataset-path ShareGPT_V3_unfiltered_cleaned_split.json \
  --num-prompts 2000 \
  --request-rate 10 \
  --max-concurrency 10 \
  --save-result \
  --result-filename baseline_results.json
```

Requests arrive at 10 per second, but `--max-concurrency 10` lets at most ten run at once, so the server spends the run near ten concurrent streams. The measured baseline:

| Metric | Measured |
|---|---|
| Total throughput (prompt + output tokens) | **474 tok/s** |
| Output throughput | **228 tok/s** |
| Mean TTFT | **104 ms** |
| Mean ITL | **43 ms** (p99 72 ms) |

Check it against the first-principles numbers before believing it:

- **ITL ≈ the weight read.** A 43 ms gap is the 42.7 ms it takes to stream 29.5 GB at 80% of 864 GB/s. Ten streams cost barely more per step than one, because the step is still memory-bound.
- **Little's law.** Ten streams at one token every 43 ms is ${}10 / 0.043 \approx 233$ tok/s, against 228 measured. The output throughput is just concurrency times per-stream speed.
- **Both SLO targets hold**: mean TTFT 104 ms &lt; 200 ms, p99 ITL 72 ms &lt; 100 ms.

This establishes **Row 00 (Baseline)** in our ledger.

## The six vLLM knobs and their physical bottlenecks

Six primary flags in `vllm serve` map directly to physical bottlenecks:

1. **`--max-num-seqs`**: Caps concurrent sequences in an iteration, directly bounding per-step decode latency and active KV allocations.
2. **`--max-num-batched-tokens`**: Sets the per-iteration token budget across prefill and decode, chunking long prompts so they do not starve concurrent decode streams.
3. **`--gpu-memory-utilization`**: Dictates the fraction of GPU memory vLLM may claim, expanding or shrinking the KV pool.
4. **`--max-model-len`**: Sets the longest accepted context length, determining worst-case per-request memory reservations.
5. **`--dtype`**: Defines numeric precision (`bfloat16`, `float16`), halving or doubling memory bandwidth requirements.
6. **`--tensor-parallel-size`**: Shards weights across multiple GPUs, distributing memory bandwidth load and expanding aggregate memory.

A startup command that sets every knob explicitly looks like this (values are a starting point to test, not a measured optimum):

```bash
vllm serve Qwen/Qwen3-14B \
  --dtype bfloat16 \
  --gpu-memory-utilization 0.90 \
  --max-model-len 8192 \
  --max-num-seqs 32 \
  --max-num-batched-tokens 2048 \
  --tensor-parallel-size 1 \
  --port 8000
```

Every continued line ends with a trailing backslash.

## Station 6 · How to read results and diagnose bottlenecks

Compare benchmark metrics against your SLO to pinpoint the bottleneck:

### Symptom A: TTFT is bad, but ITL is well within SLO
- **Diagnosis:** Prefill and queueing bottleneck. Requests wait in queue, or oversized prompts monopolize iterations.
- **Verification:** Inspect `/metrics` for high `num_requests_waiting` while `num_requests_running` is pinned at `max_num_seqs`.
- **Next experiment:** If ITL has headroom, increase `max_num_seqs` or lower `max_num_batched_tokens` to interleave prefill with decode.

### Symptom B: ITL degrades under concurrency, while TTFT is fine
- **Diagnosis:** Decode batch too large. Reading KV cache for too many concurrent sequences pushes step time past your latency target.
- **Verification:** Check `vllm:avg_decode_time_ms`.
- **Next experiment:** Reduce `max_num_seqs` to restrict concurrency to the envelope where ITL meets your SLO.

### Symptom C: KV-cache usage pinned near 100% with climbing preemptions
- **Diagnosis:** Memory pool starvation. The scheduler lacks blocks for new tokens and preempts active requests.
- **Verification:** Inspect `vllm:num_preemptions_total` and `vllm:gpu_cache_usage_perc`.
- **Next experiment:** Lower `max_model_len` to match your empirical p99 request length, or raise `gpu_memory_utilization` if headroom permits.

<Callout type="pitfall" title="Never mistake raw throughput for product success">
  Raising `max_num_seqs` increases raw throughput by amortizing weight transfers over more streams. But once the step stops being memory-bound, every extra stream lengthens every other stream's gaps, and if p99 ITL climbs past your SLO, users see stutter. Raw throughput rises while goodput falls.
</Callout>

## Station 7 · Record everything and the keep-or-revert rule

Document every run in an experimental ledger. Each entry records the isolated change, the measured numbers, and an explicit **KEEP** or **REVERT** verdict. Here is this lab's ledger, with only numbers that were measured on the L40S:

| Exp | Change (ONE knob) | Total tok/s | Output tok/s | Mean TTFT | ITL mean / p99 | Decision |
|---|---|---|---|---|---|---|
| **00** | Baseline: BF16, defaults (`max_model_len` 40,960) | 474 | 228 | 104 ms | 43 / 72 ms | **BASELINE** |
| **01** | Checkpoint: `Qwen/Qwen3-14B-AWQ` (4-bit weights) | **1,280** (2.7×) | not recorded | **59 ms** | not recorded | **KEEP**, if quality holds |
| **02** | `--max-model-len 8192` | *to run* | | | | *hypothesis below* |

**Experiment 01, read from first principles.** AWQ stores the weights in about 4 bits, and vLLM's log showed the consequences directly: weights fell from 27.5 GiB to **9.36 GiB**, and the freed memory went to the KV pool, which grew from 11.0 GiB to **29.15 GiB**, about **191,000 tokens** (${}29.15 \times 2^{30} / 163{,}840$). Decode is memory-bound, so each step now reads ${}9.36 / 27.5 = 34\%$ of the bytes: an upper bound of about 2.9× more tokens per second at the same concurrency. The run measured **2.7×** total throughput, and mean TTFT fell from 104 to 59 ms: short ShareGPT prompts are partly bound by the weight read too, and a faster server drains its queue sooner. **Verdict: KEEP, conditional** on a quality check against the BF16 model on your own evaluation set ([Measuring quality regression](/learn/quantization/measure-quality/)), because this knob traded precision for speed. The ledger records the condition, not just the speed.

**Experiment 02, written down before it runs.** Lowering `--max-model-len` from 40,960 to 8,192 raises the guaranteed concurrency from 1.76× to 8.8× (${}72{,}064 / 8{,}192$). The hypothesis: on ShareGPT at concurrency 10 the effect on throughput is small, because requests are short and the pool rarely fills; the gain is protection against preemption when a burst of long requests arrives. The cost: prompts longer than 8,192 tokens are rejected. Run it, record it, decide. If you cannot state the hypothesis and the expected sign of every column before running, you are not ready to run it.

By following the keep-or-revert rule, you ensure the system never regresses.

## The common trade-offs in LLM serving

Every optimization sits on a trade-off curve:

| Trade-off axis | Optimization choice | The gain | The compromise |
|---|---|---|---|
| **Throughput vs Latency** | Larger batch sizes (`max_num_seqs`) | Higher aggregate throughput, lower cost per token | Higher per-token latency and longer queue delays |
| **Memory vs Concurrency** | Truncating context (`max_model_len`) | Dramatically higher safe concurrent request capacity | Rejection of very long prompts at the gateway |
| **Quality vs Speed** | Quantization (preview: Module 11) | 2–3× memory reduction, larger KV pool, higher throughput | Slight loss in numerical precision or reasoning quality |
| **Cost vs Headroom** | Pushing utilization to 95% (`gpu_memory_utilization`) | Maximum token output per hardware dollar | Vulnerability to OOM crashes during request spikes |

## Looking ahead: techniques you will master

In this module, our focus has been strictly on the **method**. In subsequent modules, you will explore architectural optimizations:

- **Chunked prefill:** Splitting large prompt prefills into uniform chunks to eliminate decode stalls (you will master this in Module 10 · Prefill & Prefix Optimization).
- **Prefix caching:** Reusing cached KV blocks across requests with shared prompts (you will master this in Module 10 · Prefill & Prefix Optimization).
- **Model quantization:** Compressing weights to 4-bit and 8-bit formats like AWQ to double bandwidth efficiency (you will master this in Module 11 · Quantization).
- **Speculative decoding:** Using small draft models to verify multiple tokens in parallel (you will master this in Module 16 · Speculative Decoding).
- **Tensor parallelism:** Splitting model layers across multiple NVLink GPUs (you will master this in Module 18 · Multi-GPU Parallelism).

The engineering method remains identical: audit hardware, define workload, benchmark the baseline, change one knob, and record everything.
