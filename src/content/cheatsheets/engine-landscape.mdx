## The harness contract

Two engines are comparable **only** when all six of these are identical. Anything not on the contract is free to vary, and will.

| # | Item | What it controls for |
|---|---|---|
| 1 | **Workload** | prompt/output length distribution; shared-prefix fraction |
| 2 | **Arrival pattern** | closed-loop (N in flight) vs open-loop (fixed rate) |
| 3 | **Load point** | offered load ρ; a single value, not "as much as possible" |
| 4 | **Quality bar** | same tokens out, not similar tokens |
| 5 | **Tuning** | identical flags (measures your config) vs each engine's best (measures the engines) |
| 6 | **Version + warm state** | pinned versions; cold start reported separately |

<Callout type="recap" title="Comparison A vs B">
  **A — identical naive flags** answers "what if we deploy all of these like our current one?" Usually: all roughly the same. Run this first, to see whether the choice matters at all.
  **B — each engine at its best settings** answers "which should we run?" Costs four tuning projects and must be re-run when any engine ships. Run it only when A says the gap is worth it.
</Callout>

## Load and queueing

Offered load ρ is arrival rate as a fraction of capacity.

$$
W_q \approx \frac{\rho}{1-\rho} \times \frac{S}{B}
$$

| ρ | $W_q$ | ρ | $W_q$ |
|---|---|---|---|
| 0.50 | 1× S/B | 0.85 | 5.7× S/B |
| 0.70 | 2.3× S/B | 0.90 | 9× S/B |
| 0.80 | 4× S/B | 0.95 | 19× S/B |

- **Closed-loop** load generation flatters a slow engine: offered load falls as the server slows, so no queue forms. **Open-loop** fixes the arrival rate and the queue forms.
- SLO flips between ρ = 0.82 and 0.85 for $S \approx 2.3$ s, $B = 16$ — a **3.7% move on one knob** decides pass/fail.
- Run at **50–70%** of capacity.

## Quality parity

```python
GEN = dict(temperature=0.0, top_p=1.0, seed=0, max_tokens=256, stream=True)
```

Greedy + pinned seed + pinned **commit hash** (not a branch) + fully formatted prompt from the client. Two engines on the same weights must emit the same token IDs. If they do not, one is computing in different precision, or serving a different revision.

Three silent breakers: a moved `main` branch; different numerics by design (quantized vs FP16 — compare against a quality bar, not token for token); a server-applied chat template adding tokens you never typed.

## Is the effect real?

$$
k \approx \left(\frac{2c}{\delta}\right)^2
$$

Repeats needed to claim effect δ against rig noise c. **Reduce c first** — interleaved A/B runs are the cheapest lever there is.

| Effect δ | c = 1% | c = 5% | c = 10% |
|---|---|---|---|
| 20% | 1 | 1 | 1 |
| 6% | 1 | 3 | 11 |
| 2% | 1 | 25 | 100 |

A 6% win against 5% noise is **provisional**, not a result.

## The cost of a decode step

$$
t_{\text{step}} = \frac{\text{weights} + \text{KV read}}{\text{BW} \times \text{MBU}} + t_{\text{overhead}}
$$

- **Weights floor**: Llama-3.1-8B BF16 = 16.06 GB; at 78% of 3.35 TB/s = **6.1 ms**. No engine beats it.
- **Launch cost**: ~300 kernels × 5–10 µs ≈ **2.1 ms**, constant per step.
- That is 25% of a batch-1 step, 14% of a batch-64 step. Fixed costs matter most when the GPU work is smallest.

$$
\text{weights} = P \times b, \qquad \text{kv\_tok} = 2 \times L \times H_{kv} \times d_h \times b_{kv}
$$

## The four engines

| | vLLM | SGLang | TensorRT-LLM | llama.cpp |
|---|---|---|---|---|
| **Core idea** | paged blocks + continuous batching, Python-scheduled | radix-tree prefix cache walked in-kernel | build once, replay an execution plan | 4-bit weights, portable, no CUDA |
| **Fixed cost/step** | high of the GPU-native three | similar to vLLM | **lowest** | high |
| **Prefix reuse** | block-level, CoW | **best** | block-level, CoW | limited |
| **4-bit** | supported | supported | supported | **native** |
| **Build step** | none | none | **per configuration** | none |
| **Strongest at** | breadth, most models | prefix-heavy traffic | one fixed config, lowest latency | fitting a big model on small/non-NVIDIA HW |

Decide in this order:

1. **Does it fit?** weights + reserve vs GPU memory. Arithmetic; eliminates candidates.
2. **Hard constraints**: model support, hardware owned, build runnable in the deploy pipeline.
3. **Design vs traffic**: prefix-heavy → SGLang; fixed config, latency-critical → TensorRT-LLM; breadth → vLLM; non-NVIDIA or memory-starved → llama.cpp.
4. **Only then measure.**

## The selection matrix

$$
\text{score} = \sum_i w_i s_i, \qquad \sum_i w_i = 1
$$

- **Hard constraints run first** — no row that fails one can win on scores.
- Write the **weights before the scores**; the weight is the argument.
- **Stress the top weight ±20%.** If the winner flips, it is a judgement call — say so and name the tie-breaker.
- Never mix a measured cell with a guess in the same column.

$$
\text{goodput per dollar} = \frac{\text{good tok/s} \times 3600}{\text{GPU \$/hour}}
$$

Worked: 1,800 tok/s × 82% good at \$2.50/h → 1,476 good tok/s → **≈ 2.1 M good tokens per dollar-hour**.

## Multi-model serving & Triton Inference Server

**When it wins:** many small models, each a few percent busy, with a long tail. **When it loses:** a model that fills a card, a strict SLO on cold models, or per-tenant isolation.

$$
\text{GPUs needed} = \text{models} \times \text{utilisation per model}, \qquad
\text{monthly cost} = \text{GPUs} \times \text{price per hour} \times 730
$$

Worked: 20 models at 3% compute = 0.6 GPU of work. 20 L4s at ≈ \$0.80/h = \$16/h ≈ \$11,680/month; 2 L4s = \$1.60/h ≈ \$1,168/month. Saving ≈ **\$10,500/month**.

$$
\text{usable VRAM} = \text{GPUs} \times \text{mem} \times (1 - \text{reserve}), \qquad
\text{resident models} = \text{fit by size, not by count}
$$

**Three tiers of a model cache:**

| Tier | Hit / miss | What it costs |
|---|---|---|
| GPU VRAM | cache hit | ≈ 0 s |
| CPU RAM | warm swap | one PCIe copy |
| Disk / object store | cold load | disk read **plus** PCIe copy |

$$
t_{\text{load}} = \frac{\text{bytes}}{\text{bandwidth}}, \qquad
t_{\text{cold}} = \frac{B}{b_{\text{disk}}} + \frac{B}{b_{\text{PCIe}}}
$$

- 14 GB (7B FP16), 1 GB/s disk, 25 GB/s PCIe: **14 s + 0.56 s ≈ 14.6 s cold**, **0.56 s warm**, **0 s hot**.
- Cold is ≈ **26×** a warm swap. Quantization shrinks the bytes and therefore the load: 4-bit 7B ≈ 3.5 GB ≈ 3.5 s cold.
- **LRU evicts the oldest request first**, not the least valuable model. Report p99 including misses, never the hit rate alone.
- **Router rule 1:** send the request to a host that already has the weights. **Rule 2:** when none does, choose by memory headroom and eviction cost, and make the load visible.
- Prefer a host with the model resident over the least-loaded host. A cache miss is a 14-second detour, not a balancing opportunity.

**Triton Inference Server** (not the kernel language from Module 13):

```text
model_repository/
├── reranker/
│   ├── config.pbtxt
│   └── 1/
│       └── model.onnx
└── llama-8b/
    ├── config.pbtxt
    └── 1/
```

| `config.pbtxt` key | What it does |
|---|---|
| `platform` / `backend` | picks TensorRT, ONNX Runtime, PyTorch, Python, vLLM or TensorRT-LLM |
| `max_batch_size` | turns on batching; first dim becomes the batch dim (`-1` in `dims`) |
| `dynamic_batching` | `preferred_batch_size`, `max_queue_delay_microseconds` |
| `instance_group` | copies of the model and whether they run on GPU |
| `ensemble_scheduling` | pipeline of models inside one server request |

- Run with `--model-control-mode=explicit` to load/unload yourself:
  `POST /v2/repository/models/<name>/load` and `/unload`.
- Inference: `POST /v2/models/<name>/infer`. Defaults at the time of writing: HTTP **8000**, gRPC **8001**, metrics **8002**.
- Triton gives you the backend, batching and lifecycle primitives. **Your control plane owns the cache policy, the router and the replica counts.**
