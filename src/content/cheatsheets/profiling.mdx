## The execution model

```
thread → warp (32, lockstep) → block (one SM) → grid (the launch)
```

The hardware schedules **blocks** onto SM slots. It never schedules threads.

| Quantity | Formula |
|---|---|
| Blocks | $\lceil n / T \rceil$, $n$ elements, $T$ threads/block |
| Waves | blocks ÷ (blocks resident per SM × SMs) |
| Wave efficiency | $W / \lceil W \rceil$ |
| Registers per block | $T \times \text{regs/thread}$ |
| Blocks per SM (register limit) | $65536 / (T \times \text{regs/thread})$ |
| Occupancy | resident warps ÷ SM max warps |

- Block sizes: 32, 64, 128, 256, 512, 1024. **Use 128–512.**
- H100: 132 SMs, 64K registers/SM, ~64 max warps/SM.
- A warp is all-busy or all-idle → **divergence** costs every branch.
- Fix divergence with `torch.where`, never `if`.
- Below 1.15× wave efficiency → resize the grid or use a grid-stride loop.
- Occupancy is a **means**. Quote Speed of Light, not occupancy.

## The memory hierarchy

| Level | Size | Latency | Unit |
|---|---|---|---|
| Registers | 256 KB/SM | ~1 cycle | per thread |
| Shared memory | 256 KB/SM | ~30 cycles | 32 banks × 4 B |
| L1 / L2 | 256 KB/SM / 50 MB | ~30 cyc / ~200 ns | 128 B lines |
| HBM | 80 GB | ~600–700 ns | **32 B sectors** |

$$
\text{waste} = \frac{\text{actual traffic}}{\text{ideal traffic}} = \frac{\text{sectors} \times 32}{32 v b}
$$

| Pattern (BF16, 1 elem/lane) | Sectors | Ideal | Actual | Waste |
|---|---|---|---|---|
| `x[i]` | 2 | 64 B | 64 B | **1×** |
| `x[2i]` | 4 | 64 B | 128 B | **2×** |
| `x[8i]` | 16 | 64 B | 512 B | **8×** |
| `x[16i]` | 16 | 64 B | 512 B | **8×** (saturates) |
| `x[i][j]` (matrix column) | 32 | 64 B | 1,024 B | **16×** |

- Damage **saturates at 16×** — extra stride past one sector per lane costs nothing.
- **Shared-memory bank conflict:** a `[32][32]` column = 32-way. Pad stride to 33.
- Partial cache lines are fetched whole: keep leading dims multiples of 64 BF16.
- `transpose()` / `[::2]` views are the stride problem in disguise → `.contiguous()`.

## The roofline

$$
t \ge \max\left(\frac{F}{\text{peak FLOP/s}},\ \frac{B}{\text{bandwidth}}\right),
\qquad I = \frac{F}{B},
\qquad I_{\text{ridge}} = \frac{\text{peak FLOP/s}}{\text{bandwidth}}
$$

| GPU | Peak (BF16) | Bandwidth | Ridge |
|---|---|---|---|
| T4 | 65 TFLOP/s | 0.32 TB/s | ~203 |
| L4 | 121 TFLOP/s | 0.30 TB/s | ~403 |
| A100 80GB | 312 TFLOP/s | 2.0 TB/s | ~156 |
| H100 SXM | 989 TFLOP/s | 3.35 TB/s | ~295 |
| H200 | 989 TFLOP/s | 4.8 TB/s | ~206 |
| B200 | ~2,250 TFLOP/s | 8.0 TB/s | ~281 |

$$
\text{MFU} = \frac{F_{\text{executed}}}{\text{peak} \times t},
\qquad
\text{MBU} = \frac{B_{\text{transferred}}}{\text{bw} \times t},
\qquad
\text{headroom} = \frac{t_{\text{meas}}}{\max(F/\text{peak},\ B/\text{bw})}
$$

**Count FLOPs as executed (padding included) and bytes as transferred (waste included).**

| Kernel class | Good | Excellent |
|---|---|---|
| Large BF16 GEMM (prefill) | 55–65% MFU | 75%+ |
| Decode GEMV (m=1..32) | 75–90% MBU | 92% |
| Fused RMSNorm/RoPE | 80–90% MBU | 93% |
| Elementwise | 85–95% MBU | 97% |
| **Whole decode step** | **70–80% MBU** | 85% |

### The three fixes

| Move | Changes the bound? | Tools |
|---|---|---|
| **Raise intensity** | can cross the ridge | batching, tiling |
| **Lower bytes** | can cross the ridge | quantization, fusion, cache |
| **Improve efficiency** | no — closes the vertical gap | coalescing, occupancy, CUDA graphs |

Below 1.15× headroom → **stop**.

## The profiling funnel

```
PyTorch profiler → Chrome trace → Nsight Systems → Nsight Compute
    where?           gaps?          when & what?      why is this kernel slow?
```

```python
# 1 · framework level. Warm up FIRST — the first passes allocate and autotune.
for _ in range(5): model(input_ids)
torch.cuda.synchronize()
with profile(activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA],
             record_shapes=True, profile_memory=True) as prof:
    for _ in range(10): model(input_ids)
    torch.cuda.synchronize()
print(prof.key_averages().table(sort_by="self_device_time_total", row_limit=20))
prof.export_chrome_trace("trace.json")          # open in Perfetto / chrome://tracing
```

```bash
# 2 · whole timeline
nsys profile --trace=cuda,nvtx,osrt --sample=none --duration=30 -o decode python serve.py

# 3 · one kernel
ncu --kernel-name regex:"gemm|flash" --launch-count 1 --set full python serve.py
```

| Timeline pattern | Diagnosis | Owner |
|---|---|---|
| Solid GPU row, idle CPU | GPU-bound | optimize the longest kernel |
| GPU row full of 2–5 µs gaps | **launch-bound** | Module 15 |
| Busy CPU, idle GPU | CPU-bound | reduce host work |
| Big periodic NCCL bar | comm stall | Module 18 |
| `cudaMalloc` mid-run | allocator thrash | preallocate |

### Three stall reasons cover almost everything

| Stall | Meaning | Fix |
|---|---|---|
| **Long Scoreboard** | waiting on memory | more warps, fewer bytes, better locality |
| **MIO Throttle** | shared-memory/SFU queue full | bank conflicts, fewer `__syncthreads()` |
| **Wait / No Instruction** | instruction-cache miss | serialize less, reduce divergence |

**The 80% rule:** above 80% of Speed of Light, stop. Sort by **headroom**, not duration.

## Prefill vs decode

Profile them as **two separate experiments**.

$$
B_{\text{decode}} = \underbrace{P \cdot b_w}_{\text{weights}} + \underbrace{B \cdot T \cdot b_{kv}}_{\text{KV}}
$$

$$
T_{\text{crossover}} = \frac{122{,}500}{B} \quad \text{(Llama-3.1-8B, BF16, KV/token = 131,072 B)}
$$

| Batch | Crossover context |
|---|---|
| 8 | 15,300 |
| 32 | 3,830 |
| 128 | 957 |

| | Prefill | Decode |
|---|---|---|
| Rows per GEMM | 512+ | 1 per sequence |
| Intensity | ~410 | ~10 |
| Bound | compute | memory |
| **Quote** | **MFU** 55–65% | **MBU** 75–90% |
| Biggest fix | fuse elementwise ops | lower bytes |
| Fusing SiLU·mul | **real win** | **noise** (L2-resident) |
| Bigger batch | ~free | **the biggest lever** |

## Reference numbers (Llama-3.1-8B, BF16, H100)

| Quantity | Value |
|---|---|
| KV bytes / token | 131,072 (128 KiB) |
| Weights | 16.1 GB |
| Ridge point | 295 FLOP/byte |
| Decode bytes (B=32, T=8k) | 16.1 + 34.4 = 50.5 GB |
| Decode floor at 76% MBU | 20 ms |
| Decode compute term | 0.8 ms (96% of units idle) |
| Prefill chunk (512 tok) at 60% MFU | 13.8 ms GEMM, ~21 ms total |
| Attention intensity | $T / 8$ FLOP/byte |

## The five numbers of a report

1. **Step time** (measured, warmed up)
2. **Byte budget** — weights / KV / attention
3. **Intensity** and the **ridge point** (so the bound is checkable)
4. **The metric that matches the bound** — MBU or MFU
5. **Headroom** — and a residual-risk section

## The five sentences

1. **Find the bound first** — intensity against the ridge — or you are optimizing at random.
2. **Quote the efficiency that matches the bound.** MBU for decode, MFU for prefill; the other number is noise.
3. **Count the bytes the hardware moved**, not the bytes you wanted. Wasted sectors are 8–16× and invisible in your source code.
4. **Profile prefill and decode separately.** Same kernels, opposite answers.
5. **Above 80% of the speed of light, stop** — and write down the residual risk.
