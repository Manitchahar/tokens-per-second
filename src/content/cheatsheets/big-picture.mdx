## The life of a request

**client → gateway → router → serving engine → scheduler → kernels → GPU hardware**

- **Prefill**: whole prompt in one parallel pass. Fills the KV cache, produces token 1. <span class="ink k-compute">Compute-bound</span>.
- **Decode**: one token per step, each step reads all weights and the KV cache. <span class="ink k-memory">Memory-bound</span>.
- **KV cache**: stored keys and values of every past token. Grows by one entry per token.

## The seven request path layers & tuning levers

| Layer | Component | What an inference engineer tunes |
|---|---|---|
| 1. Client | Browser, CLI, App | SSE streaming chunk buffers, timeouts, retry backoff with jitter |
| 2. Gateway | Envoy, Nginx | Token-bucket rate limits, context payload size limits, admission control |
| 3. Router | Load balancer | Least-connections routing, prefix / cache-aware routing |
| 4. Serving engine | vLLM, SGLang | `gpu_memory_utilization` (e.g. 0.90), tensor parallelism (`--tp`), block size |
| 5. Scheduler | Iteration scheduler | `max_num_seqs`, `max_num_batched_tokens`, chunked prefill, preemption |
| 6. Kernels | CUDA, Triton | FlashAttention-2/3/FlashInfer, GEMM tiling, fused RMSNorm + RoPE |
| 7. Hardware | GPU, HBM, NVLink | Core/memory clock locking (`nvidia-smi -lgc`), power limits, NUMA affinity |

## Model lifecycle: from training to serving

1. **Data Curation**: Raw data ingest, cleaning, tokenization.
2. **Training & Fine-Tuning**: Iterative backpropagation, optimizer states (16–20 bytes/param), compute-bound on GPU clusters.
3. **Evaluation**: Offline benchmarks (MMLU, GSM8K), loss validation.
4. **Packaging & Conversion**: SafeTensors, quantization (AWQ, GPTQ, FP8), engine graph compilation.
5. **Serving**: Low-latency forward pass only, dynamic continuous batching, frozen weights, KV cache management under strict SLOs.
6. **Monitoring & Iteration**: TTFT/TPOT telemetry, error rates, data drift logging feeding retraining.

### Training vs serving frameworks

| Dimension | Model Training | Production Serving |
|---|---|---|
| Weights | Updated via backpropagation | Frozen (read-only) |
| Goal | Minimize loss | Latency, throughput, cost-to-serve at fixed quality |
| Memory | Dominated by Adam optimizer states | Dominated by static weights and dynamic KV cache |
| Batching | Large, static batches | Dynamic, iteration-level continuous batching |

## The four numbers

- **Latency**: TTFT (first token) and TPOT (per token while streaming).
- **Throughput**: output tokens/s over all users.
- **Memory**: weights + KV cache + workspace.
- **Cost**: dollars per million tokens.

$$
T_{\text{total}} = t_{\text{gateway}} + t_{\text{queue}} + t_{\text{prefill}} + (n-1)\cdot t_{\text{step}}
$$

$$
\text{TTFT} = t_{\text{gateway}} + t_{\text{queue}} + t_{\text{prefill}}
$$

- When TTFT spikes under load, queue wait time $t_{\text{queue}}$ (not GPU compute) is usually the primary cause.

$$
\text{throughput} = \frac{B}{t_{\text{step}}}, \qquad \text{per-user speed} = \frac{1}{t_{\text{step}}}
$$

$$
\text{memory} = \text{weights} + B \cdot \text{ctx} \cdot \text{KV bytes/token} + \text{workspace}
$$

$$
\text{\$/M tokens} = \frac{\text{GPU \$/hr}}{\text{tok/s} \times 3600} \times 10^{6}
$$

## Rules of thumb

- One-user decode ≈ **weights bytes ÷ memory bandwidth**. 16 GB on an H100 (~2.7 TB/s usable) ≈ 6 ms per token.
- Batching reuses each weight read for every user: throughput rises almost linearly until KV reads or math catch up.
- The **KV cache**, not the model, usually limits how many users fit.
- Raising batch size: throughput ↑, per-user speed ↓, memory ↑, cost per token ↓.
- Always report **all four** numbers, plus hardware and batch size.

## Timing GPU code

```python
torch.cuda.synchronize(); t0 = time.perf_counter()
out = model(x)
torch.cuda.synchronize(); dt = time.perf_counter() - t0
```

GPU calls are asynchronous. No synchronize = wrong numbers.
