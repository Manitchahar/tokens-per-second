## The core philosophy

> **A model that answers vs a model that acts.**
> A standard LLM predicts tokens from static weights. An agent enters an autonomous control loop: it gathers fresh environment state, decides actions dynamically, verifies outcomes, and persists across multiple turns.

---

## The fundamental agent control loop

```
┌────────────────────────────────────────────────────────┐
│                   THE AGENT CYCLE                      │
│                                                        │
│   1. PERCEIVE ───► Ingest state, goal, tool schemas    │
│         │                                              │
│         ▼                                              │
│   2. PLAN     ───► Reason over state; select next move │
│         │                                              │

│         │                                              │

```

## Compounding error arithmetic

### Independent Step Reliability
If each step succeeds with independent probability $p$, the probability of completing a $k$-step trajectory without error is:

$$
P(\text{task success}) = p^k
$$

### The Reliability Cliff
| Step Accuracy ($p$) | 1 Step ($k=1$) | 3 Steps ($k=3$) | 5 Steps ($k=5$) | 10 Steps ($k=10$) | 20 Steps ($k=20$) |
|:---|:---|:---|:---|:---|:---|
| **80% (0.80)** | 80.0% | 51.2% | 32.8% | 10.7% | 1.2% |
| **90% (0.90)** | 90.0% | 72.9% | 59.0% | 34.9% | 12.2% |
| **95% (0.95)** | 95.0% | 85.7% | 77.4% | **59.9%** | **35.9%** |
| **98% (0.98)** | 98.0% | 94.1% | 90.4% | 81.7% | 66.8% |
| **99% (0.99)** | 99.0% | 97.0% | 95.1% | 90.4% | 81.8% |

### The Half-Life Step Horizon
The number of steps $k_{\text{half}}$ before overall success drops to a coin flip (50%):

$$
k_{\text{half}} = \frac{\ln(0.5)}{\ln(p)} \approx \frac{0.6931}{1 - p}
$$

- At $p = 0.95$: $k_{\text{half}} \approx 13.9$ steps.
- At $p = 0.90$: $k_{\text{half}} \approx 6.9$ steps.
- At $p = 0.99$: $k_{\text{half}} \approx 69.3$ steps.

## Tool classification and blast radius

| Tool Tier | Category | Examples | Side Effects | Blast Radius | Approval Policy |
|:---|:---|:---|:---|:---|:---|
| **Tier 1** | **Knowledge (Read)** | Vector search, SQL SELECT, file read | None (Idempotent) | **Low** (Data leakage) | Autonomous |
| **Tier 2** | **Capability (Compute)** | Python AST sandbox, calculator, regex | Transient CPU/RAM | **Medium** (Timeouts, OOM) | Sandboxed |
| **Tier 3** | **Action (Write)** | SQL UPDATE/DELETE, bash exec, API mutate | Permanent mutation | **CRITICAL** (Data loss) | **Mandatory HITL Gate** |

### Rule of Least Privilege
- Never grant write credentials directly to the model.
- Require Human-In-The-Loop (HITL) approval with a **structured dry-run diff** for all Tier 3 actions.
- Use Abstract Syntax Tree (`ast.parse`) validation; **never call raw `eval()`**.

## Tool schema overhead & prefix cache arithmetic

- Average token cost per well-formed JSON Schema: **150 to 250 tokens**.
- For $M$ tools across $K$ turns:

### Without Prefix Caching ($O(K^2)$ quadratic waste):
$$
\text{Total Prefill Tokens} = K \cdot L_0 + \Delta \frac{K(K - 1)}{2}
$$
- For $L_0 = 1{,}500$, $\Delta = 500$, $K = 10$: **37,500 prefill tokens**.

### With Prefix Caching ($O(K)$ linear efficiency):
$$
\text{Total Prefill Tokens (Cached)} = L_0 + (K - 1) \Delta
$$
- For the same task: **6,000 prefill tokens** (84.0% compute savings!).

> **Cache Invalidation Warning:** Never place dynamic timestamps, session UUIDs, or random IDs at the start of an agent prompt. Any prefix change collapses cache hit rate from 95% to 0%.

## Planning architectures: ReAct vs DAG vs Reflexion

| Dimension | ReAct | Plan-then-Execute | Reflexion |
|:---|:---|:---|:---|
| **Core Paper** | Yao et al. (2022) | Plan-and-Solve | Shinn et al. (2023) |
| **Flow** | `Thought -> Action -> Obs` | Planner (70B) $\to$ DAG $\to$ Workers | Trial $\to$ Evaluator $\to$ Critique $\to$ Retry |
| **Execution** | Strictly serial | **Parallel DAG dispatch** | Multi-episode sequential |
| **Wall-Clock Time** | High ($K \times T$) | **Lowest** ($\text{critical path}$) | Very high ($M \times K \times T$) |
| **Token Volume** | Moderate (2k – 8k) | Low-Moderate (1.5k – 4k) | High (10k – 30k) |
| **Prefix Caching** | Monotonic append (Great) | Shared planner prefix | Reset between trials |
| **Best For** | Dynamic investigation | Parallel research, data ETL | Complex coding, algorithmic math |

### Parallel Speedup
For $N$ independent tools with model latency $T_{\text{LLM}}$ and tool latency $T_{\text{tool}}$:
$$
T_{\text{ReAct}} = N \times (T_{\text{LLM}} + T_{\text{tool}}) + T_{\text{final}}
$$
$$
T_{\text{DAG}} = T_{\text{planner}} + \max(T_{\text{tool}}) + T_{\text{synth}}
$$
- For $N = 4$, $T_{\text{LLM}} = 1.0\text{s}$, $T_{\text{tool}} = 0.2\text{s}$: ReAct takes **5.8 s**; DAG takes **2.4 s** (58.6% faster).

## Memory management: the hybrid compaction buffer

### The Three Tiers
1. **Working Context Window (Tier 1):** GPU HBM / KV Cache. Bandwidth: 2.0 – 3.35 TB/s. Capacity: 4k – 128k tokens. Short-term RAM.
2. **External Stores (Tier 2):** Vector DB / SQL / NVMe disk. Bandwidth: 100 MB/s. Capacity: Infinite. Long-term episodic memory.
3. **Parametric Memory (Tier 3):** Transformer weights $\theta$. Static, frozen at inference.

### The Anchor-Summary-Recent Architecture
Never use naive FIFO sliding window truncation (which evicts the initial goal and induces catastrophic amnesia). Use the 3-part layout:

```
[ANCHOR HEAD]         System prompt + active tool schemas + original user goal (Never truncated)
      ▼
[COMPACTION BUFFER]   Dense structured JSON summary of older turns (Verified facts & disproven causes)
      ▼
[RAW RECENT TAIL]     Last 3 to 5 raw turns preserved with full detail for step-by-step reasoning
```

### Fixed Token Budget Equation
$$
B_{\text{total}} = B_{\text{anchor}} + B_{\text{summary}} + B_{\text{tail}} + B_{\text{gen}} \le B_{\text{max}}
$$
- Standard allocation on a 4,096-token budget:
  - $B_{\text{anchor}} = 1{,}500$ tokens
  - $B_{\text{summary}} = 400$ tokens
  - $B_{\text{tail}} = 1{,}500$ tokens
  - $B_{\text{gen}} = 696$ tokens

## Defensive failure engineering & evaluation

### Loop Detection via Canonical State Hashing
Compute SHA256 of sorted tool name and canonical arguments:

$$
H_t = \text{SHA256}(\text{tool\_name} + \text{json.dumps}(\text{args}, \text{sort\_keys}=\text{True}))
$$

- Trip circuit breaker if $H_t$ repeats 3 consecutive times.
- Inject a synthetic corrective observation directing the agent to pivot.

### The Four Core Metrics
1. **Pass@1 Success Rate:** $\frac{N_{\text{solved}}}{N_{\text{total}}} \times 100\%$
2. **Trajectory Efficiency:** $\bar{K}_{\text{solved}} = \frac{1}{N_{\text{solved}}} \sum_{i \in \text{solved}} K_i$
3. **Cost per Solved Task:**
   $$
   C_{\text{solved}} = \frac{\text{Total Fleet Cost}}{N_{\text{solved}}} = \frac{\bar{C}_{\text{run}}}{\text{Success Rate}}
   $$
4. **Agent Goodput:** Solved tasks meeting the latency SLO per second.
